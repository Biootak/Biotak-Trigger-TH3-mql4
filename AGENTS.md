## Build (Windows)

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File compile-th3.ps1 -Project all
powershell -NoProfile -ExecutionPolicy Bypass -File compile-th3.ps1 -SourceFile ".\Biotak Trigger TH3 Lite.mq4"
```

Success = `Result: 0 errors` in `build-logs/`. Never compile `.mqh` directly.
After BMP changes: recompile, then remove & re-add the indicator in MT4
(icons load only at attach). Full deploy: `powershell -File tools/deploy.ps1`.
Linux: `./compile-th3-linux.sh all` (isolated Wine prefix, terminal stays open).

From the agent side the same script is called as `& .\compile-th3.ps1 -Project all`
(the PowerShell tool already IS PowerShell, and `powershell.exe` from Bash is
blocked by policy), after `$env:APPDATA` is set and the six `*_proxy` variables
are nulled — otherwise it cannot resolve the MQL4 directory. The tool may return
no stdout; redirect to a file and read it (`*>` writes UTF-16).

Nulling them needs `[System.Environment]::SetEnvironmentVariable($n, $null,
'Process')`, not `Set-Item env:$n -Value $null`: the PowerShell `env:` provider is
case-insensitive, so it leaves the second case of the pair behind and
`Start-Process` (compile-th3.ps1:691) then dies with «Item has already been added.
Key in dictionary: 'http_proxy' Key being added: 'HTTP_PROXY'» — a FAIL that is
the environment, not the code. Null both cases of each pair, in the SAME
invocation as the compile; shell state does not persist between tool calls.
`-Project all` builds only the MAIN entry (workspace + installed) — every `.mq4`
needs its own `-SourceFile` run.

**The number under test.** The master's figure is `1403` and it is a lower bound
he declines to open: two of his three named axes (ترتیب, زاویهٔ حرکتی) are
unbounded, the second of them continuous, so the space as stated has no finite
count. The census tool does not try to reach `1403` — it proves `1403` is
unreachable for a reason rather than an opinion: it is ODD (`23 x 61`), and any
grammar carrying a symmetric `جهت` axis multiplies by 2, so every legal total is
EVEN. The taught skeleton enumerates to `960`; stretching exactly one unsourced
axis (cover delay `1..4` -> `1..6`) lands on `1440`, which is also `2 x 6!` —
«۲ جهت × ترتیب قرار گیری شش کندل».

**Provenance, because it is easy to get wrong.** Nothing drawn or enumerated
here comes from Bulkowski's thepatternsite.com. Every schematic, every axis and
the whole 1440 census are built from the Trex course itself (the TREX METHOD
channel plus the course PDF). Bulkowski contributes exactly one number, cited
only as an outside yardstick, and that number is narrower than it looks: `103`
is their **ranked** set («All ranks are out of 103 candlestick patterns»), read
directly from `CandleEntry.html` / `Hammer.html` — their own index headline says

candlesticks. So `103` is a studied-set size, not a census. The site also carries
an explicit no-AI-training notice in its footer; treat it as a citation target,
never as content to copy.

Do not quietly substitute a stretched axis for a sourced one: `--solve` reports
how many axes each hit had to move, and that count is the honesty check.

Three rules this file exists to enforce. **One:** a candle arrangement is
authored in ATR units (`ATR == 100`), so «۸۰٪ شدو» and «۲.۵ × ATR» are literal
numbers in the data rather than a drawing someone eyeballed. **Two:** in the
curated gallery every card renders into the same fixed viewBox, so the whole
atlas composes into one SVG by translation and 1 ATR is the same size in every
card. **Three:** the census wall is the deliberate exception — it auto-fits each
cell, because 1440 silhouettes at a shared scale are illegible. The page says so
in prose; if that sentence ever disappears, the two modes have blurred into one
and the gallery's shared-scale claim is no longer trustworthy.

Break any of these and the atlas still looks fine while becoming misleading.

The page loads **Vazirmatn** from Google Fonts for its own UI, but every
exported SVG pins `font-family="Tahoma, Arial"` on purpose: an export is a file
that has to render on a machine with no network and possibly no Vazirmatn, so
the webfont must not leak into it. The palette is a similar contract — the
chrome is deliberately low-chroma so the only loud things on the page are the
data (candle blue/red, the amber imaginary line, the jade export buttons).

## The skeleton axes (`Biotak/TH3/`)

TH3 used to store X/A/B/C plus one number. It could not say *which arrangement*
it had drawn, because the course's axes had no representation — so the step had
nothing to be found `FROM`. Five axes now exist and are measured off the bars:

| Axis | Type | Measured from |
|---|---|---|
| Momentum | `TH3_MOMENTUM` | the impulse leg's **speed**, `R = \|A->B\| / (ATR(trigger) * sqrt(elapsed / barMinutes))`, banded by `MOMENTUM_SPEED_*` (1.00 / 1.30 / 1.60) |
| Pivot candle | `TH3_PIVOT_CANDLE` | the candle at B, in chart-ATR units (`0.80 / 1.20 / 2.50`) |
| Cover depth | `TH3_COVER_DEPTH` | the first candle after B that reverses B's range: does it take B's body, and how many older candles does it engulf |
| Cover delay | `int` | candles from B to that covering candle |
| Direction | `int` | `pB > pA` |

## The course's own pivots (`Biotak/TH3/TH3Pivots.mqh`, P-TH3-P6)

The six-condition pivot is now a PRODUCT detector, ported from the course PDF
itself (pp. 6-7 pivot, p. 3 fractal TFs, p. 50 shared pivots) — not from the
research encoding in `tools/step_from_retrace.py`, whose numbers were the
researcher's choices (0.25 confirm dial, 0.5 close gate). The PDF's own
numbers: side candles < 4 (else a BASE pivot), a run of >= 3 standard candles
or >= 240% ATR travel, a >= 80% same-TF ATR reversal, a master candle (80%
body or 80% shadow) covered — or, if not a master, a hypothetical 1-ATR line
covered — and the covering candle closing in its final third. The detector
runs on ANY timeframe against that TF's own ATR (`TH3SixPivotsScanTF`), the
chain steps by the course's factor of four (`TH3FractalStepTF`: 1-5-15-60-240-
1440-10080-43200; M30 is not a chain member), structure = one step up, and a
chart pivot a structure pivot claims wears the higher TF (`shared`, p. 50).
Application: `inpTH3AutoPivots` (dialog input, default on) draws the pivots —
chart-TF triangles (up below a low, down above a high, ~one candle
clear of the wick), structure-TF triangles in the structure ink, shared
in the structure ink — and `TH3PivotSnap` lands the draw-session's X/A/B/C clicks on the nearest found
pivot, so a hand-drawn pattern sits on the same candles the detector read.
The scan is cached per new bar of its own TF; markers repaint per new chart
bar or 5 s, bulk-clearing their own `TH3_P6_` namespace (teardown in
OnDeinitHandler). Lite compiles the detector (domain) but not the markers
(UI half, P-BUILD-01 — the EventHandlers calls sit under `#ifndef BUILD_LITE`).

They live in `TH3Skeleton` (TH3Types.mqh), are filled by
`TH3SkeletonFromBars()` and packed by `TH3SkeletonKey()` into a mixed-radix
coordinate — **4 x 4 x 4 x 6 x 2 = 768 cells**. That is deliberately *not* the
atlas's 1440: the atlas enumerates 8 pivot-candle arrangements and 3 momentum
classes, these are the 4-and-4 measurable subset. Do not "fix" one to match the
other; reaching a particular count was never the goal, having a coordinate was.

The step comes from `TH3StepFromSkeleton()`, which is course method 1:

```
long  = 3*ATR(structure) - 2*ATR(pattern)
med   = 2*ATR(structure) -   ATR(pattern)
short = (long + med) / 2      // momentum band picks which one
```

`ATR(structure)` reads **completed daily bars only** (shift 1,
P-TH3-STEP-01): shift 0 is the forming day, whose partial range biased
the frozen-for-the-day cache ~6% low early in the day (measured −5.8% at
h02 → −0.2% at h22 on the broker's own daily series). The function's own
20-bar fallback already read bars 1..20; the primary path now agrees.

Three rules here that must not be relaxed. **The momentum bands select in
ASCENDING order of size** — WEAK the smallest, NORMAL the middle, STRONG and
EXPLOSIVE the largest. `short` is a blend, `0.5*(long + med)`, so it sits BETWEEN
the other two rather than below them; the shipped assignment handed it to WEAK
and thereby ran the axis backwards over its own middle band on every chart where
the pattern ATR is under the structure ATR, which is every intraday chart.
Measured over 22,538 real legs: WEAK `2.264 S` against NORMAL `1.870 S`, i.e.
`+21.1%` of step for a weaker impulse. **`3S - 2P` goes non-positive as soon as
the pattern's ATR exceeds 1.5x the structure's** — the course's own formula does
this. That returns `false` with the output untouched, never a negative or zero
step, because a negative step is not a small step, it is no step. And the
cover-depth/cover-delay multipliers (0.70-1.0) are **deliberate choices, not
course numbers**; they are the only tunable part of the function and are marked
as such in the code.

The momentum bounds are `1.00 / 1.30 / 1.60` in R units. `R = 1` is kept exact,
because it is the only bound with a meaning independent of any sample: below it a
leg travelled less than the trigger timeframe's own ATR predicts for its duration,
and the measured p25 is 1.01, so honouring it costs a `0.01` shift. The other two
are read off the R ladder (`p50 1.28`, `p75 1.63`). They are **not** the old
degree bands' quantiles, which preserved a mix that put 82.7% of legs in the top
two bands and left the axis inert; the mix is now 24.1 / 27.7 / 21.4 / 26.7 and
STRONG-or-better is 48.1%. Note the third bound is a **label only**: STRONG and
EXPLOSIVE select the same candidate, so it never moves the step.

An unmeasurable pattern carries `skeleton.valid == false` and `key == -1`. It is
never filled with a plausible default, so "unmeasured" stays distinguishable from
"a standard pivot with no cover" all the way out to the log and the label.

The live chart label shows both steps side by side — the percentage (a share of
AB) and the skeleton reading in pips — because they are two different answers to
"how big is a step" and the skeleton one is the one that can be checked against
the market. `Biotak_TH3_Test.mq4` pins every band boundary, the non-positive-step
edge, and injectivity of the packed key.

The drawn ladder now follows the course's own step (P-TH3-STEP-02, refined
P-TH3-STEP-05, PDF p. 2: گام حرکتی = ATR تایم پترن): its base unit comes from
the one owner `TH3PatternStepRung()` — the pattern TF's own ATR(14) off the
last completed bar (P-TH3-STEP-01's shift-1 rule). It used to read
`THAbilityPrice` (the professor's fractal-ladder rung), but that number is a
DIFFERENT ruler (H1: 72.9 pips vs that TF's own ATR 185.3) and it is why step 3
drew cramped next to C; the thousand-chart survey behind this validated
step3/ATR ≈ 1.0, not step3/rung, so the rung was replaced, not tuned. Step 3 =
3 rungs lands on the course's co-level pivot (p. 50, ~3× of 80..120% ATR) —
the market must react at step 3 (and 5); other TFs are the same grid,
fractally, because every rung (including the walked-up owner TF's) is an ATR
of its own TF. The AB-percentage cut survives only as the fallback
when no rung answers. And the course's own update rule (p. 2: after price has
reacted to the rungs, recalibrate them) is `TH3HitPivotMeasure` (P-TH3-STEP-03,
strict from P-TH3-STEP-04b): step = |C−tip|/3, k fixed at 3, and the tip is
NOT the furthest extreme — reading the continuation (rung 5's own level) as
the tip and dividing by 3 built a 29.7 step out of an 18.0 one. It is the
first local extreme of the reaction (P-TH3-STEP-04c — a pivot match is
corroboration, not the arithmetic) that has travelled **one full step**
(P-TH3-STEP-04d: `dist >= 3 rungs`; a shallower bounce is SKIPPED, the walk
asks the next extreme, and it never votes). Without that floor a 2-rung wiggle
was read as step 3 and rebuilt the ladder 33% smaller than the market had
proven — `step` came out below the rung, i.e. the step drew cramped next to the
pivot tip. With it the proved step can only equal or WIDEN the rung, and a
chart whose market has not reached step 3 keeps `TH3PatternStepRung()`
untouched. The tip is then matched to the nearest six-condition pivot, whose TF
comes with the answer (`hasPivot` words the verdict, `touches` = separate
crossings); the NEXT pivot of the same kind is only the witness (`k5Err`,
reported not fitted), and
the proof draws itself — dotted C→tip plus the `T3 <- M15 H x2 (0.4%)` verdict OFF
the tip (P-TH3-STEP-11: one half-band plus margin past it, keeping its anchor

orange). That verdict is only drawn when the market actually voted
(P-TH3-STEP-06): with no pivot at the tip and no grid adopted there is no
proof, so the interval and the label are DELETED rather than left advertising a

and the number is the height actually drawn. The rule stays strict by design

no pivot of the chart's own layers at the tip means the grid belongs to a
bigger TF — the chain is walked UP (`TH3SixPivotsHasPivotAt`) and its rung
is adopted instead. A live-drawn pattern cannot see its own reaction yet, so
`TH3HitPivotForward` (P-TH3-STEP-04) re-measures the ACTIVE pattern's proof
on every tick (`OnCalculate` calls it directly) and re-draws only when a proof
the chart does not yet carry exists. **That re-measure is a memo, not a walk
(P-TH3-PERF-08):** the ladder is rebased from one pattern far more often than
its inputs move — per tick by the forward pass, per drag event and per settings
redraw by `DrawABCDPattern` — so the two heavy rebase reads (`TH3RealDAt`, the
real-D walk, and `TH3HitPivotMeasure`, the tip + crossings walk) are memoised
one slot each in `TH3Pivots.mqh`. The key is every input plus `iBars(NULL, 0)`
(the chart's own bar count — the structure TF's bar can only close on a chart
bar's edge, so it is the stricter clock) and `Period()`; refusals
("no reaction reached the floor yet", "price never left C") are memoised like
any other answer, and arming is the ONE exit past each key guard, so a key that
was checked is a key that was written. `Biotak_TH3_Test.mq4` §12 pins it with
the hit/miss counters `TH3RebaseMemoHits()` / `TH3RebaseMemoMisses()`: a
repeated rebase is a HIT, a changed price or rung is a MISS. And a stacked double info no longer lies about the step: only
one pattern info is ever visible (P-TH3-P6d).

## The hand-set lines (P-UI-98/98d/99, 2026-09-21)

Two lines the user's hand sets: the custom price line, and — new — the FIRST
step. User order: «در مود کاستوم پرایس step اول قابل ویرایش باشه که کاربر با
درگ کردن از همون جا گام دلخواهشو در تمام مود ها بتونه اعمال بکنه که به صورت
خودکار با همون نسبت ها در تایم ها دیگه اعمال بشه» — and, only step 1, never the
rest.

**The handle IS the trigger line ONE STEP from the custom price line.** The
pipeline draws the trigger lines at the MIDPOINT of each pair of neighbouring
levels, and the custom price line is a zone EDGE (the ladder's centre sits half
a step above it), so the drawn family is `start + 1*step, +2*step, ...` above
and `start + 0*step, -1*step, ...` below: `_Below_1` IS the custom price line.
`Step1HandlePick` (LevelPipeline) therefore chooses by geometry — per side, the
line nearest one step from the custom price, never one closer than half a step
— and the below handle is `_Below_2`. Its face (SELECTABLE, z-order above the
zone fills, the tooltip) is owned by `Step1HandleOwnFace` in LevelPipeline's
render — AFTER `CreateOrUpdateHLine`, whose fresh objects are born
`SELECTABLE=false` (a face write before creation landed on nothing and the
handle stayed un-grabbable — the reported «الان step اول قابل درگ کردن نیستش»).
The face's rung is written unguarded: the zorder audit bans `OBJPROP_ZORDER`
reads in product code (P-UI-31's rule).

**The override is ONE factor.** `StepOverrideFactor()` (GlobalVariables,
chart-scoped GVar `Biotak_StepFactor_<chartId>`) multiplies the mode factory's
stepSizes in `DrawLevelsBasedOnMode` — the SS/LS pair keeps 1.5 : 2.0, the
Factor harmonic pair its ratio, and a TF switch re-scales the new TF's natural
steps by the same F («با همون نسبت ها در تایم ها دیگه»). The drag math divides
by the F-FREE first step the factory noted (`NaturalFirstStepNote`), never a
re-derivation. F is a term of the geometry signature (`frameCore`), or a drag
reads as the same picture (P-UI-52's trap with a new seat). The `S:` pips in
the mode label and the Factor label ride the same factor. It resets with the
placement (teardown + R key) and dies on REASON_REMOVE.

**The armed/SET contract (P-UI-98d).** User order: «وقتی بعد جابجایی روش کلیک
شد ست نهایی بشه و با دبل کلیک فعال بشه؛ تا زمانی که ست نهایی نشده آزادنه درگ
بشه». ARMED = draggable — since P-UI-98e through the handle's OWN carry (the
custom price line's channel, P-UI-49c), with the P-UI-98 OBJECT_DRAG channel

budget.

کردن روش ندزده» half). A single click sets (deferred past the double-click

## Does the pivot actually repeat? (`tools/pivot_repeatability.py`)

The atlas draws what the course *says*. These two tools ask whether it *works*,
on the broker's own bars, read straight off disk by `tools/mt4_history.py`.
There is no reason to invent a market or call an API: the terminal already holds
the exact bars the indicator would have seen, and this machine has 96 `.hst`
files (~399,000 bars, 0 unusable).

```
python tools/mt4_history.py                 # inventory every .hst on this machine
python tools/mt4_history.py --selftest      # re-derives the binary layout from raw bytes
python tools/pivot_repeatability.py --selftest
python tools/pivot_repeatability.py --survey --symbols 8              # feature lift
python tools/pivot_repeatability.py --sweep  --symbols 8              # 36 configs
python tools/pivot_repeatability.py --cross "run_bars>=5" --tf 1440   # across series?
python tools/pivot_repeatability.py --ftc --symbols 8                 # the FTC level claim
python tools/pivot_repeatability.py --ftc-hold --symbols 8            # does FTC hold?
```

**The `.hst` layout was measured, not looked up.** Header 148 bytes; record
stride 60; timestamp at +0, then open/**high/low/**close at +8/+16/+24/+32 — note
that is not `MqlRates` order (open/low/high/close), which is why the first three
probes read as garbage. `detect_layout()` re-derives header and stride from the
bytes and refuses to trust the constants, so a terminal upgrade fails loudly.

**Lift is the only currency here.** A pivot's success rate alone is meaningless
— price moves. Every rate is reported against the identical race started at
every bar's close in the same direction, and a feature only counts if the sign
and rough size survive in **both halves** of every series (`worst_half`).

**Three traps are baked into the code as named selftest seeds**, each one a
mistake this tool actually made:

1. **Look-ahead.** An ATR zigzag labels a bar a swing high *because* price later
   fell, so counting the forward move from that bar measures information already
   spent. `swings()` returns `confirm_idx` and every race is entered at the
   confirming bar's close. Seed B2 asserts the gap stays open.
2. **A test that cannot fail.** Comparing FTC's distance to the next turning
   point against X/Y/midpoint proved nothing: all anchors sit ~2 ATR from the
   next swing just by being near the price. Each FTC test now compares against a
   **shuffle** (same levels, pairings broken). Seed H fires the permutation test
   on planted data and keeps it quiet on noise.
3. **A sample that differs per cell.** Scanning level offsets while admitting
   any level inside the window's range shrank the sample as the offset rose, and
   the survivors were the windows that bounced hardest — fabricating a tidy
   +0.25 ATR peak. The common-subset filter is the fix, and its note explains why
   that earlier peak was an artifact.

**What the corpus currently says** (8-12 daily series, ~2,500 pivots):

- Pivot class as a directional trigger: **lift ≈ 0**. Sweep of 36 configurations
  (horizon 5-40, target 0.5-2.0 ATR, zigzag 0.5-2.0 ATR): **0 of 36** cleared
  +2pp, while ~1.8 would clear it by chance.
- `FTC = (X+Y)/2 + TH` sits within a quarter-ATR of the pivot high `X` in **84.9%**
  of cases, so "FTC reacts" is largely the same statement as "the pivot high
  held" — true by construction. The next turning point lands ~1.8 ATR **below**
  FTC (k=0 hit rate 0.00%), and FTC holds *worse* than `X` (39.2% vs 41.3%).
- The one candidate the sweep surfaced, `run_bars >= 5` (+8.4pp pooled, stable
  across all four horizons), **fails its holdout**: positive in 8/11 series with
  a sign test p = 0.11 and every per-series CI covering the null. Pooled lift
  came from pooling, not from members agreeing.

None of this rejects the course. It measures one narrow claim — *pivot geometry
alone predicts a fixed-ATR directional move at daily scale*. The course trades
nested timeframes off a trigger TF, and the pivot detector here is a 1-ATR zigzag
plus anatomy features, not the six-condition pivot. Widening the test means
intraday timeframes and the real six conditions, not loosening the yardstick.

## Tool environment (Windows, this machine)

The app runs the **PowerShell tool** through a ConPTY — inside its own terminal —
and sets `CODEBUDDY_POWERSHELL_USE_PTY=1` for the CLI. The **Bash tool** runs with
pipes and **no console** (`stdoutMode=pipe`, `stdinMode=pipe` in
`logs/sandbox/*/sandbox_*.log`), so every console program it spawns is handed a
brand-new console, which Windows 11 gives to its default terminal app (Windows
Terminal): an external window, failing `0x800700e8` (ERROR_NO_DATA) on handoff.

The safe-delete guard is what spawns one: bash's `rm`/`rmdir`/`unlink` shims
(`cli/vendor/shim/safe-bin/rm` → `safe-delete-common.sh`) run
`node.exe safe-delete-bulk-guard.cjs check --target …`. So:

- **Never delete with `rm`/`rmdir`/`unlink` from Bash.** Use the PowerShell tool
  (`Remove-Item`), whose guard override is a `function global:Remove-Item` that
  runs in-process inside the app's own terminal. Paths under `%TEMP%` are skipped
  by the guard entirely.
- Prefer the PowerShell tool for anything that spawns a console program.
- Bulk deletes need the user's approval; a blocked or denied delete leaves the
  file in place — report it, never route around it.

## Working rules

- Git stays connected. No `git status` gate, no dirty-tree block. Work
  directly on files; commit only on request.
- Comments carry `P-XX-NN` trap IDs and `-OFF` markers (e.g. `PANELDRAG-OFF`,
  `BKCURSOR-OFF`, `BKMAGNET2-OFF`, `VIEWLOCK-OFF`, `STEPOVERRIDE-OFF`).
  `-OFF` = retired in place: restore by uncommenting the marked sites and
  re-teaching the named gate, never by rewriting. A restored one is marked
  `-ON` (e.g. `TH3TOOL-ON`, 2026-09-19 — the TH3 tool and its panel card are
  live again; its ring slot is APPENDED as `RING_TH3`, so no other slot moved).
  That item is a DRAWING control, so a press ARMS the AB=CD session (one owner:
  `CircArmTH3Draw()`, which repairs the engine/mode preconditions, swallows the
  arming press instead of spending it as pivot X, and arms through the same
  `ToggleTH3Tool` the V key uses), the light is the armed session, and the
  ENABLED switch lives in the card's row 0 (P-UI-96). A session never writes
  `CHART_EVENT_MOUSE_MOVE`: that flag is chart-scoped and shared with the ring,
  the panels and BaseKnot, so its ONE writer is `OnInitHandler` (P-TH3-PERF-07).
  Every TH3 ink — preview, points, labels, lines, the target ladder, the zones —
  is resolved by `TH3InkForChart` (lightness only, hue kept, identity on a dark
  chart), and the preview borrows the committed pattern's own settings through
  `TH3SessionPointInk` / `TH3SessionLineInk`, so a drawn letter can no longer be
  invisible on a white chart nor promise a colour the pattern will not keep
  (P-UI-97). A dark chart is deliberately left alone: the inks there are the
  user's own choice, which is why the shipped inputs are `clrDarkBlue`.
- Perf law: never write a chart property you would not change (MT4 repaints on
  every `ObjectSet*`); teardown/show-hide are bulk operations; every saver
  writes through a shadow and only one `GlobalVariablesFlush` exists.
- MT4 facts that bite: `OBJECT_DRAG` carries no trusted cursor (read live
  anchors); a motionless press/release emits no `MOUSE_MOVE` (gestures need a
  poll shadow); `id=1` is `OBJECT_CLICK`; writing a natively-dragged object
  cancels its drag; icons/`ex4` load only at attach.
- P-TIME-01 (2026-09-22) — ONE CLOCK: server time only. `TimeLocal()` (the
  Windows clock) appears nowhere in `Biotak/`; chart-facing text never prints
  GMT (history files may store it, the chart never shows it); `TH3LOG`/`TH3CAP`
  lines carry their own server stamp (`st=`, epoch) so rows from two machines
  stay comparable without trusting log prefixes.

  stay outside. Full history (superseded details, old `AGENTS.md`/`LEARNING.md`)
