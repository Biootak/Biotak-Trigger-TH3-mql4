## Layout

- Entries (thin stubs, event handlers only): `Biotak Trigger TH3.mq4` (Full),
  `Biotak Trigger TH3 Lite.mq4` (Lite, `#define BUILD_LITE` inside it).
- All logic: `Biotak/*.mqh`, layered bottom-up, composed in the entries via
  `Biotak/EventHandlers.mqh`. A module may only depend on modules below it;
  includes at top only; every `.mqh` include-guarded.
- Settings: `Biotak/RuntimeSettings.mqh` is the single owner (mirrors,
  `#define inpX gX`, seeding, `OV_*` persistence). Seed via
  `RuntimeSettingsInit()` first in `OnInitHandler`; never read `inpX` in a seed
  below the `#define`s (silent no-op). `FF_` enum addresses never renumber.
- Indicator-wide state: `Biotak/GlobalVariables.mqh`. Panel-editable state:
  `RuntimeSettings.mqh`, not GlobalVariables.
- Trade-plan math: `Biotak/TradePlanFormulas.mqh` only. Icons: `Files/Icons/*.bmp`,
  generated by `node tools/gen-th3-icons.js`, embedded via `#resource`.

**P-UI-113c (2026-09-23) — THE OPENING PRESS OWNS ITS OWN CLICK-FAMILY EVENTS.**
Reported: «چرا با رها کردن هولد استریپ هم بسته میشه». The hold fires while the

**P-DRAW-30 (2026-09-24) — THE PANEL BECOMES TWO, ON THE CARDS' OWN NUMBERS.**
User report, with the box's Settings open and the plate taller than the window:
«چرا مثل بقیه پنل ها جمع و جور نیستش و به دو تا [ستون] تبدیل نمیشه مثل همونا باشه

`PNL_WEL` / `PNL_WIDE_WEL` 624 / `PNL_COL_DX` 312 / `PNL_WIDE_MIN_ROWS` 10); the

for a 740 px chart — and read as nothing like the cards it sits beside.

The fix is deliberately the cards' OWN arithmetic, not a lookalike: `DSTRIP_GEAR_W`
(312) keeps its meaning (ONE column's width), `DSTRIP_GEAR_W2` 624 and
`DSTRIP_GEAR_COL` 312 are `PNL_WIDE_WEL` / `PNL_COL_DX`, and
`DSTRIP_GEAR_WIDE_ROWS` 10 is `PNL_WIDE_MIN_ROWS` — `[drawstrip-box-panel]`
PARSES both modules and fails if the two ever drift apart, which is the difference
between "looks like the cards" and "is measured like the cards". Each column is
the same 280 px content the narrow layout always used (16 px pads, the middle
32 px is the two pads back to back), so every block metric above it — swatch 28,
chip 64, row 42 — keeps its arithmetic and NOTHING else had to be re-tuned.

HOW IT IS BUILT, in three passes inside `DrawStripGearLayout()`: the content is
built ONCE in the narrow column's own y-space (`DrawStripGearContent()`, the tab
chain as it always was), a section call OPENS A BLOCK (`s_dsGearBlkY`, "this header
and the content under it" — the cards' band rule, `PnlRowFull`), and then
`DrawStripGearPlace()` decides and TRANSLATES:

  * the rule is the TAB's own content, so a narrow tab stays narrow and no tab
    inherits another's columns (every item's column is reset before the decision);
  * two or more blocks: the split is the contiguous boundary that MINIMISES the
taller column — reading order is kept (left column top-to-bottom, then the right),
    and a section header can never leave the rows it labels;
  * one block (a fibo's Levels is a single section of list rows): there is no
    boundary to choose, so the ROW RUN splits at its own middle and the header
    stays at the top of the left column;
  * every item is moved by `newColumnTop - its own y` and wears its column:
    grids bake the shift into their own X (the P-DRAW-27 hover hit test reads it
    back), rows/sections/edits carry `s_dsGRCol` / `s_dsGearSecCol` /
    `s_dsGearEditCol` the painters add. The plate's height stays `48 + 42k` (the
    skin's own arithmetic) either way, so the 9-slice and the grippers are
    untouched.

**P-UI-113j / P-DRAW-37 (2026-09-25) — THE PRESS NAMES ITS OWN DRAWING, AND A RIDE
MOVES INSTEAD OF REBUILDING.** Reported, for the third time in this gesture's
history: «موقع که ابجکت سلکت هستش من موس روش نگه میدارم استریپ باز میشه ولی رها که
میکنم بسته میشه جالبتر اینکه اگر ابجکت مثل باکس که سلکت نباشه درست کار میکنه». The
two existing witnesses both fail on a SELECTED drawing, and the code says why:

* `DrawStripReleaseOnDrawing` (P-UI-113i) asks the release pixel for the drawing
  through `DrawObjectAt` — and the only test that accepts a drawing's own CONTROLS
  (`DrawHitSelectedHandle`, P-UI-113h) is consulted for the objects whose
  `OBJPROP_SELECTED` reads true AT THAT MOMENT. MT4 commits its selection change
  around the click (the same fact P-UI-113f/g were written for), so a release on the
  handle the hand is holding resolves to `""` = outside click = the TV-style
  dismissal closes the strip the hold just opened. An unselected drawing is grabbed
  on its BODY (that is the only test a non-selected object passes), so its release
  stays on the body and the same code works — the asymmetry the user describes.
* the opening window (`s_dsOpenerUntil`, P-UI-113c) was disarmed by a LATE press
  edge: the press edge is `tleft && !s_dsLeftPrev` on the move stream, and a selected
  drawing is moved by MT4 itself while the hand rests on it, so the terminal reports
  moves whose button bit does not match one continuous press. Every such edge ran
  `DrawStripOpenerDisarm()` AND re-ran the latch, restarting the 500 ms clock
  (P-UI-113b's shape, from the other side).

The fix is one fact instead of two re-derivations: **the hold latch already
hit-tests the press pixel** (`DrawObjectAtCached`), so it KEEPS that answer for the
whole press cycle (`s_dsPressCycleObj`, bounded by the press's own cap) and the
release asks it BEFORE it asks any pixel or any selection state. A press cycle
already named is never re-declared: a late edge keeps the owner, the press point,
the travel (now measured from the true press point, so a still press is a click and
a drifting one is a drag — honest for the zero-move press too) and the opening
window. `s_dsPressTracked` is set by the latch, not only by the move edge.

**P-DRAW-37, the same walk's architecture finding.** `DrawStripOpenAt` treated a
re-open of the SAME object (the drawing's own drag, a zoom, a scroll, a re-anchor)
as a fresh open: `DrawStripClose()` (the whole ~40-object family deleted) then
rebuild. That is where P-UI-113e/g's snapshot-and-restore dances came FROM — two
windows that existed only to survive a round trip that never had to happen — and it
ran at the drag's own 50 ms cadence on the weakest machine. A ride is now
`DrawStripRide()`: one anchor projection, the hand's offset kept, layout+paint; the

Three rules this file exists to enforce. **One:** a candle arrangement is

## The skeleton axes (`Biotak/TH3/`)

TH3 used to store X/A/B/C plus one number. It could not say *which arrangement*
it had drawn, because the course's axes had no representation — so the step had
nothing to be found `FROM`. Five axes now exist and are measured off the bars:

| Axis | Type | Measured from |
|---|---|---|
| Momentum | `TH3_MOMENTUM` | the impulse leg's **speed**, `R = \|A->B\| / (ATR(trigger) * sqrt(elapsed / barMinutes))`, banded by `MOMENTUM_SPEED_*` (1.00 / 1.30 / 1.60) |
| Pivot candle | `TH3_PIVOT_CANDLE` | the candle at B, in chart-ATR units (`0.80 / 1.20 / 2.50`) |
| Cover depth | `TH3_COVER_DEPTH` | the first candle after B that reverses B's range: does it take B's body, and how many older candles does it engulf |
| Cover delay | `int` | candles from B to that covering candle |
| Direction | `int` | `pB > pA` |

## The course's own pivots (`Biotak/TH3/TH3Pivots.mqh`, P-TH3-P6)

The six-condition pivot is now a PRODUCT detector, ported from the course PDF
itself (pp. 6-7 pivot, p. 3 fractal TFs, p. 50 shared pivots) — not from the
old research encoding (a script since deleted, P-TOOL-04), whose numbers were the
researcher's choices (0.25 confirm dial, 0.5 close gate). The PDF's own
numbers: side candles < 4 (else a BASE pivot), a run of >= 3 standard candles
or >= 240% ATR travel, a >= 80% same-TF ATR reversal, a master candle (80%
body or 80% shadow) covered — or, if not a master, a hypothetical 1-ATR line
covered — and the covering candle closing in its final third. The detector
runs on ANY timeframe against that TF's own ATR (`TH3SixPivotsScanTF`), the
chain steps by the course's factor of four (`TH3FractalStepTF`: 1-5-15-60-240-
1440-10080-43200; M30 is not a chain member), structure = one step up, and a
chart pivot a structure pivot claims wears the higher TF (`shared`, p. 50).
Application: `inpTH3AutoPivots` (dialog input, default on) draws the pivots —
chart-TF triangles (up below a low, down above a high, ~one candle
clear of the wick), structure-TF triangles in the structure ink, shared
in the structure ink — and `TH3PivotSnap` lands the draw-session's X/A/B/C clicks on the nearest found
pivot, so a hand-drawn pattern sits on the same candles the detector read.
The scan is cached per new bar of its own TF; markers repaint per new chart
bar or 5 s, bulk-clearing their own `TH3_P6_` namespace (teardown in
OnDeinitHandler). Lite compiles the detector (domain) but not the markers
(UI half, P-BUILD-01 — the EventHandlers calls sit under `#ifndef BUILD_LITE`).

They live in `TH3Skeleton` (TH3Types.mqh), are filled by
`TH3SkeletonFromBars()` and packed by `TH3SkeletonKey()` into a mixed-radix
coordinate — **4 x 4 x 4 x 6 x 2 = 768 cells**. That is deliberately *not* the
atlas's 1440: the atlas enumerates 8 pivot-candle arrangements and 3 momentum
classes, these are the 4-and-4 measurable subset. Do not "fix" one to match the
other; reaching a particular count was never the goal, having a coordinate was.

The step comes from `TH3StepFromSkeleton()`, which is course method 1:

```
long  = 3*ATR(structure) - 2*ATR(pattern)
med   = 2*ATR(structure) -   ATR(pattern)
short = (long + med) / 2      // momentum band picks which one
```

`ATR(structure)` reads **completed daily bars only** (shift 1,
P-TH3-STEP-01): shift 0 is the forming day, whose partial range biased
the frozen-for-the-day cache ~6% low early in the day (measured −5.8% at
h02 → −0.2% at h22 on the broker's own daily series). The function's own
20-bar fallback already read bars 1..20; the primary path now agrees.

Three rules here that must not be relaxed. **The momentum bands select in
ASCENDING order of size** — WEAK the smallest, NORMAL the middle, STRONG and
EXPLOSIVE the largest. `short` is a blend, `0.5*(long + med)`, so it sits BETWEEN
the other two rather than below them; the shipped assignment handed it to WEAK
and thereby ran the axis backwards over its own middle band on every chart where
the pattern ATR is under the structure ATR, which is every intraday chart.
Measured over 22,538 real legs: WEAK `2.264 S` against NORMAL `1.870 S`, i.e.
`+21.1%` of step for a weaker impulse. **`3S - 2P` goes non-positive as soon as
the pattern's ATR exceeds 1.5x the structure's** — the course's own formula does
this. That returns `false` with the output untouched, never a negative or zero
step, because a negative step is not a small step, it is no step. And the
cover-depth/cover-delay multipliers (0.70-1.0) are **deliberate choices, not
course numbers**; they are the only tunable part of the function and are marked
as such in the code.

The momentum bounds are `1.00 / 1.30 / 1.60` in R units. `R = 1` is kept exact,
because it is the only bound with a meaning independent of any sample: below it a
leg travelled less than the trigger timeframe's own ATR predicts for its duration,
and the measured p25 is 1.01, so honouring it costs a `0.01` shift. The other two
are read off the R ladder (`p50 1.28`, `p75 1.63`). They are **not** the old
degree bands' quantiles, which preserved a mix that put 82.7% of legs in the top
two bands and left the axis inert; the mix is now 24.1 / 27.7 / 21.4 / 26.7 and
STRONG-or-better is 48.1%. Note the third bound is a **label only**: STRONG and
EXPLOSIVE select the same candidate, so it never moves the step.

An unmeasurable pattern carries `skeleton.valid == false` and `key == -1`. It is
never filled with a plausible default, so "unmeasured" stays distinguishable from
"a standard pivot with no cover" all the way out to the log and the label.

The live chart label shows both steps side by side — the percentage (a share of
AB) and the skeleton reading in pips — because they are two different answers to
"how big is a step" and the skeleton one is the one that can be checked against
the market. `Biotak_TH3_Test.mq4` pins every band boundary, the non-positive-step
edge, and injectivity of the packed key.

The drawn ladder now follows the course's own step (P-TH3-STEP-02, refined
P-TH3-STEP-05, PDF p. 2: گام حرکتی = ATR تایم پترن): its base unit comes from
the one owner `TH3PatternStepRung()` — the pattern TF's own ATR(14) off the

## The hand-set lines (P-UI-98/98d/99, 2026-09-21)

Two lines the user's hand sets: the custom price line, and — new — the FIRST
step. User order: «در مود کاستوم پرایس step اول قابل ویرایش باشه که کاربر با
درگ کردن از همون جا گام دلخواهشو در تمام مود ها بتونه اعمال بکنه که به صورت
خودکار با همون نسبت ها در تایم ها دیگه اعمال بشه» — and, only step 1, never the
rest.

**The handle IS the trigger line ONE STEP from the custom price line.** The
pipeline draws the trigger lines at the MIDPOINT of each pair of neighbouring
levels, and the custom price line is a zone EDGE (the ladder's centre sits half
a step above it), so the drawn family is `start + 1*step, +2*step, ...` above
and `start + 0*step, -1*step, ...` below: `_Below_1` IS the custom price line.
`Step1HandlePick` (LevelPipeline) therefore chooses by geometry — per side, the
line nearest one step from the custom price, never one closer than half a step
— and the below handle is `_Below_2`. Its face (SELECTABLE, z-order above the
zone fills, the tooltip) is owned by `Step1HandleOwnFace` in LevelPipeline's
render — AFTER `CreateOrUpdateHLine`, whose fresh objects are born
`SELECTABLE=false` (a face write before creation landed on nothing and the
handle stayed un-grabbable — the reported «الان step اول قابل درگ کردن نیستش»).
The face's rung is written unguarded: the zorder audit bans `OBJPROP_ZORDER`
reads in product code (P-UI-31's rule).

**The override is ONE factor.** `StepOverrideFactor()` (GlobalVariables,
chart-scoped GVar `Biotak_StepFactor_<chartId>`) multiplies the mode factory's

The atlas draws what the course *says*. Two scripts (`tools/mt4_history.py`,
`tools/pivot_repeatability.py`) asked whether it *works*, on the broker's own bars
read straight off disk — **both deleted with the suite (P-TOOL-04)**. What
survives is the measurement they produced, kept because the numbers are the
result and the code was only the instrument. There is no reason to invent a
market or call an API: the terminal already holds the exact bars the indicator
would have seen, and this machine has 96 `.hst` files (~399,000 bars, 0 unusable).
Re-running any of it means writing the reader again from the layout notes below.


**The `.hst` layout was measured, not looked up.** Header 148 bytes; record
stride 60; timestamp at +0, then open/**high/low/**close at +8/+16/+24/+32 — note
that is not `MqlRates` order (open/low/high/close), which is why the first three
probes read as garbage. `detect_layout()` re-derives header and stride from the
bytes and refuses to trust the constants, so a terminal upgrade fails loudly.

**Lift is the only currency here.** A pivot's success rate alone is meaningless
— price moves. Every rate is reported against the identical race started at
every bar's close in the same direction, and a feature only counts if the sign
and rough size survive in **both halves** of every series (`worst_half`).

**Three traps were baked into the deleted code as named selftest seeds**, each
one a mistake that tool actually made — kept so the same mistake is not made
twice:

1. **Look-ahead.** An ATR zigzag labels a bar a swing high *because* price later
   fell, so counting the forward move from that bar measures information already
   spent. `swings()` returns `confirm_idx` and every race is entered at the
   confirming bar's close. Seed B2 asserts the gap stays open.
2. **A test that cannot fail.** Comparing FTC's distance to the next turning
   point against X/Y/midpoint proved nothing: all anchors sit ~2 ATR from the
   next swing just by being near the price. Each FTC test now compares against a
   **shuffle** (same levels, pairings broken). Seed H fires the permutation test
   on planted data and keeps it quiet on noise.
3. **A sample that differs per cell.** Scanning level offsets while admitting
   any level inside the window's range shrank the sample as the offset rose, and
   the survivors were the windows that bounced hardest — fabricating a tidy
   +0.25 ATR peak. The common-subset filter is the fix, and its note explains why
   that earlier peak was an artifact.

**What the corpus currently says** (8-12 daily series, ~2,500 pivots):

- Pivot class as a directional trigger: **lift ≈ 0**. Sweep of 36 configurations
  (horizon 5-40, target 0.5-2.0 ATR, zigzag 0.5-2.0 ATR): **0 of 36** cleared
  +2pp, while ~1.8 would clear it by chance.
- `FTC = (X+Y)/2 + TH` sits within a quarter-ATR of the pivot high `X` in **84.9%**
  of cases, so "FTC reacts" is largely the same statement as "the pivot high
  held" — true by construction. The next turning point lands ~1.8 ATR **below**
  FTC (k=0 hit rate 0.00%), and FTC holds *worse* than `X` (39.2% vs 41.3%).
- The one candidate the sweep surfaced, `run_bars >= 5` (+8.4pp pooled, stable
  across all four horizons), **fails its holdout**: positive in 8/11 series with
  a sign test p = 0.11 and every per-series CI covering the null. Pooled lift
  came from pooling, not from members agreeing.

None of this rejects the course. It measures one narrow claim — *pivot geometry
alone predicts a fixed-ATR directional move at daily scale*. The course trades
nested timeframes off a trigger TF, and the pivot detector here is a 1-ATR zigzag
plus anatomy features, not the six-condition pivot. Widening the test means
intraday timeframes and the real six conditions, not loosening the yardstick.

## Tool environment (Windows, this machine)

The app runs the **PowerShell tool** through a ConPTY — inside its own terminal —
and sets `CODEBUDDY_POWERSHELL_USE_PTY=1` for the CLI. The **Bash tool** runs with
pipes and **no console** (`stdoutMode=pipe`, `stdinMode=pipe` in
`logs/sandbox/*/sandbox_*.log`), so every console program it spawns is handed a
brand-new console, which Windows 11 gives to its default terminal app (Windows
Terminal): an external window, failing `0x800700e8` (ERROR_NO_DATA) on handoff.

The safe-delete guard is what spawns one: bash's `rm`/`rmdir`/`unlink` shims
(`cli/vendor/shim/safe-bin/rm` → `safe-delete-common.sh`) run
`node.exe safe-delete-bulk-guard.cjs check --target …`. So:

- **Never delete with `rm`/`rmdir`/`unlink` from Bash.** Use the PowerShell tool
  (`Remove-Item`), whose guard override is a `function global:Remove-Item` that
  runs in-process inside the app's own terminal. Paths under `%TEMP%` are skipped
  by the guard entirely.
- Prefer the PowerShell tool for anything that spawns a console program.
- Bulk deletes need the user's approval; a blocked or denied delete leaves the
  file in place — report it, never route around it.

## P-DRAW-64a fifth cut + P-DRAW-64 addendum 6 (2026-09-27) — THE 50 % IS A LEVEL, AND THE INTERIOR RIDES THE HAND

**Two reports, one build, and the first one kills a payload the second one never needed.**

**1. The 50 % cell was a LENGTH, and the user wants a LEVEL.** «خود باکس رو از وسط طول
نصف میکنه که نباید باشه / من میخوام فقط 50 درصد مثل فیبو که 50 درصد مشخص میشه مثل
اون باشه / اون دکمه 50 درصد که زدم اوکی» — the button is right, the BEHAVIOUR is wrong.
So `DRAW_SLOT_BOXHALF` writes the `[BX50]` MARK and nothing else: the level is
`BoxMidSync`'s `<box>_BX50` dotted line at the box's own mid PRICE, the same idiom a fib
uses, drawn by the owner that already owned it, and **no anchor of the drawing moves**.
The length the hand drew is the length the box keeps.

**What that deletes, and why deleting is the honest half.** The cell used to be the
state AND the payload: `[BXH:<seconds>]` remembered the length so the second tap could
put it back, and `BoxHalfRecheck` (pump + release witness) dropped the mark whenever a
hand gave the box a length that was no longer half — a whole staleness rule that exists
only because the cell cut the box. A level is true for EVERY box, at every length, in
every position, so it has no payload and nothing to re-check: `DrawBoxHalfSpan`,
`DrawBoxHalfRead`, `DrawBoxHalfWrite`, `BoxHalfRecheck` and its two call sites are
DELETED, not parked. A box drawn by an earlier build still carries a `[BXH:…]`; it means
nothing now and the next mark write drops it with the rest of the group, so no migration
is needed. The `[BX50]` bake was not touched — a solid block with a dashed midline is
literally "this box's 50 %", and the user said the button is fine. Two smaller truths the
change exposed: the 50 % and the travelling far edge no longer fight over one edge (the
level is a horizontal line, the extend is a time), so the "one owner" hand-off in the
extend's write is gone and both can be on together; and the cap loses `DRAW_CAP_BOXHALF`
on CHANNEL / FIBOCHAN / ELLIPSE / TRIANGLE, because a channel's third anchor and an
ellipse's are not that mid price and C-04 forbids a control where nothing would happen.

**2. The interior's lag was never a missing witness — it was a coalesced event AND a
second layer.** «این باکس که جابجا میکنه این fill ازش جا میمکون بعد چند میلی ثانیه بعدش
جفت میشه», and then the diagnosis itself, with the log refused: «فقط رنگ‌کشی یک فریم عقب‌تر
است». Three builds had already answered the SHAPE of that report by moving the sync (out
from under the 50 ms throttle, P-DRAW-64 addendum 4; to the head of the router, above every
guard, addendum 5) and it still lagged, which is the measurement that says the WITNESS was
never the problem — `FillChildSync` runs in the very event that moved the master, so the
data is correct before anything is painted. Two causes were left, and both are now closed:

- **(a) THE EVENT COALESCES.** MT4 merges a run of identical ids, so a dropped
  `OBJECT_DRAG` frame is a frame the interior did not move in — a hand at 60 Hz watches
  the box leave its fill behind and sees it catch up when the next frame lands. The move
  stream does not coalesce (every pixel of travel is its own event) and the press already
  named the object (`s_dsPressObj`, P-UI-113i), so `FillChildStamp` rides it behind a
  four-value memo: a still frame costs four reads and one compare, a real move the guarded
  sync, an idle hand one string compare, and the arming also rides the drag event so a
  gesture MT4 reports only as `OBJECT_CHANGE` is covered. The release witness stays as the
  last word.
- **(b) THE INTERIOR WAS IN THE OTHER LAYER.** This is the one frame the report names, and
  it was a line of code: the child was created with a hard `OBJPROP_BACK = true` — behind
  the bars — while the box is in front. MT4 paints the layer the dragged object lives in
  as the drag moves it, so an interior parked in the other layer is painted by the NEXT
  pass. No amount of stamping can close that, because the write is already correct when
  the paint happens. The child now MIRRORS the box's own `OBJPROP_BACK` (one guarded
  compare per sync, a write only when the box's layer really changed), so box and interior
  share one paint pass, and the strip's BACK cell became one honest switch for the whole
  drawing instead of a hidden rule that put the interior somewhere the box was not.

**The one visible consequence, stated rather than buried:** a filled box in the foreground
now covers the candles inside it, exactly like every filled rectangle MT4 draws, and the
BACK cell is what puts the interior behind the bars with its box. That trade is the
price of a frame-exact interior, and it is the user's to see rather than mine to hide.

**3. The 50 % line is a whisper, and a whisper is written once.** «خط وسط باید نازک تر ...
مینمال باشه که چارت شلوغ نشه», with the architecture asked for by name and the budget
«هزینه صفر یا نزدیک به صفر». Two lines were making it the loudest thing a quiet box can
wear, and both were free to remove:

- **THE FRAME MIRRORED THE BOX'S.** `BoxMidSync` wrote `OBJPROP_WIDTH` from the master's
  own width on every sync, so a 2-3 px box got a 2-3 px dotted rule in the same ink as
  its border — and paid a read plus a compare to keep it that way. The frame is now
  written at BIRTH (`OBJPROP_WIDTH 1`, `STYLE_DOT`) and never touched again: the steady
  state loses a read and a compare, and the line is the thinnest thing MT4 can draw.
- **THE INK WAS AT FULL STRENGTH.** The level wore the master's colour exactly, so it
  competed with the border it was supposed to sit quietly inside. It now wears that
  colour blended `BOX_MID_FADE 55` percent towards the cached chart background — the
  same owner and the same arithmetic the interior's tone already uses, one cached read
  and one blend, and the guarded setter means a still frame writes nothing.

**What was deliberately NOT done, and why that is the architecture.** A fib prints its
level's price on the left; adding it here would be a SECOND object per box, a caption
owner, and pixels the user just asked to lose. The line also keeps the box's full width,
because a level that stops short of the edges is a tick, not a level. And the sync keeps
its 50 ms drag throttle with its one description read per throttled frame: 20 reads a
second of a short string is not a cost worth a memo, and a memo here would have to be
invalidated by the mark's writer to stay honest — coupling the geometry to the tag for
microseconds is the wrong trade.
