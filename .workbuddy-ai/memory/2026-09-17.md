## Investigation (read-only, no code changed): "our box is not like MT4's"

User report (16:25) + screenshot of MT4 with our Base Box next to a native MT4
rectangle. Asked to check the official MQL4 docs.

Forensics on the screenshot (real size 1920x1080, crop + pixel map):
- TOP box = MT4's own: border `rgb(0,0,255)` 3px + **5 anchor squares 7x7**
  (4 corners + centre), each with a 1px white centre pixel.
- BOTTOM box = OURS: border `rgb(0,0,139)` (DarkBlue) 4px + **zero anchors**.
- `Biotak/PropertiesAndInputs.mqh:184` `inpBoxBorderColor = C'0,0,139'` proves the
  bottom box is ours.

Root cause found: `BaseKnotCommit` (`Biotak/BaseKnotTool.mqh:5096-5101`) creates the
box and sets SELECTABLE / HIDDEN / TIMEFRAMES / TOOLTIP but **never
`OBJPROP_SELECTED`**. MT4 only paints its own selection markers (centre + corner
squares) on a SELECTED object — and with BKGRIP-OFF those markers ARE the only
resize handles. The module's single `OBJPROP_SELECTED, true` write (line 3964,
`BaseKnotGripReselect`) is dead since `BK_GRIP_COUNT 0` (line 3748).
=> Our box is one state short of MT4's own: MT4's freshly drawn rectangle stays in
edit mode; ours commits unselected, so it wears no points and needs one extra click.

Docs checked (docs.mql4.com): `OBJPROP_SELECTED` = "Object is selected",
`OBJPROP_SELECTABLE` = "Object availability"; MT4's own rule for a selected shape =
sizing dots at the centre and along the edges, edge/corner dot = resize, centre dot
= move the whole shape.

Proposed fix (NOT applied, awaiting user decision): one write at commit,
`ObjectSetInteger(0, box, OBJPROP_SELECTED, true);`. Trade-off flagged: P-UI-45 (a
selected object is moved by MT4 on any later chart drag); guard is P-BK-63's
outside-click drop, which does not cover a drag. `panel-wiring-audit.py:2144-2175`
has gates around the SELECTED owner that would need re-teaching.

`C:\Users\Bioootak\.workbuddy-ai\binaries\python\envs\default` and installed Pillow
there for screenshot forensics (PowerShell `Add-Type` is blocked by policy).

### SECOND FINDING — the CLASS read is anchored to the OPEN CHART, not the box

Found while answering «ftr etr غیره چطور مشخص میشه». The type itself is
ATR-free, but it is NOT fully chart-invariant either:

- `BaseKnotBaseTFMin` (`BaseKnotTool.mqh:2765`) takes no TF argument; it reads

- Inside, the candidate ladder is built **upward from `chartMin`** (`:2737-2745`,

  fallback is `return chartMin;` (`:2752`) — "a base of THIS chart's TF".

## P-BK-77/78 — the node's TIME is chart-independent, and the three abilities are the LADDER's

User (screenshot + words): «درست تشخیص نمیده گره باید ETR باشه تایم گره یک ساعته هستش سه

تایم گره درست تشخیص داده بشه که فرقی نکنه در چه تایم فریمی هستیم».

**Root cause — three leaks, all of them let the CHART decide:**
1. `BaseKnotRungHoldCount` had `if(tfMin == Period()) return BK_BASE_RUNG_MIN;` — this
   chart's own TF confirmed itself WITHOUT reading a single candle.
2. The ladder only walked UPWARD from the box' TF, so a node whose candles stood still on
   a LOWER rung than the box' TF could never be named.
3. The admission test was `3 * rung / chartMin > bars` — CHART candles admitted rungs.

**The fix (user's own three choices):**
- Which rung is the node's time when several stand still → **the HIGHEST rung**.
- Where the three abilities come from → **ATR of the node's time / one rung above / two
  rungs above** (P-BK-78). The `BK_AB_TRIG_RATIO 0.25` / `BK_AB_PAT_RATIO 0.50` ratios are
  GONE: they could only express «a fraction of this TF's ATR», never «belongs to a HIGHER
  time».
- When no rung stands still → **the span's own rung** (the smallest rung one candle of
  which covers the span), never the chart's TF.
