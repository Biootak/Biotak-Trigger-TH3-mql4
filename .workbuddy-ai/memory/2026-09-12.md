Chain: load valid file -> heuristic says legacy -> `FileDelete` -> `loadedCount=0` ->

## P-PERF-19..20 — the cache nobody called, and the lock behind every read — NOT COMMITTED

## What the log actually said (read from MQL4/Logs/20260912.log, plain UTF-8)

```
21:58:37  [W][PERF] OnDeinit reason=4 took 984ms (budget 150ms)      <- no breakdown line yet
22:55:31  [W][PERF] baseInit breakdown: file=0ms migrate=312ms rebuild=0ms
                    cleanup=47ms (fileStamp=5 entries=48)
22:55:31  [W][PERF] OnInit (ok) [ind=375 ui=0 settings=0 hist=0 base=375 atr=0]
22:55:32  [W][PERF] OnInit (ok) [ind=313 ui=0 ... base=313 ...]
```

Two facts, both new:
1. **A stamped, no-rebuild file still costs 312 ms inside the load window.** The
   P-PERF-11 self-destruct loop is gone (`rebuild=0`, `fileStamp=5`, `entries=48`), and
   the seconds moved into a window that had ONE stamp covering four unrelated jobs.
2. The 21:50/21:58 OnDeinit lines have no breakdown because that build predates the
   P-PERF-15 ledger; from the next deploy the line will name its phase.

## The find: the base-price state is a mutex, and its cache had no callers

`BasePriceManager.mqh` declares the "legacy globals" as TEXT macros:

```
#define g_basePriceCached (g_symbolStates[GetSymbolStateIndex()].basePriceCached)
... 7 of them, ~115 use sites across the repo
```

and `GetSymbolStateIndex()` is not a lookup - it is a mutex built from terminal global
variables: `Symbol()`, 2x `GlobalVariableCheck`, `TimeCurrent()`, 2x
`GlobalVariableSet`, 2x `GlobalVariableTemp`, 2x `GlobalVariableDel`, plus a bounded
retry loop (`LOCK_MAX_ATTEMPTS 5 x LOCK_RETRY_DELAY_MS 20`). So **every read of the base
price, the history count or the initialised flag took a lock**: on the tick path
(`g_basePriceCached` in `RedrawAllObjects`), all through init and the per-day save, and
inside loop CONDITIONS (`for(i = 0; i < g_historyCount; i++)` = one lock cycle per
entry, three sites).

`GetCachedSymbolStateIndex()` - the cheap, symbol-guarded, live-range-guarded wrapper -
**existed and had ZERO callers**; only its LRU invalidation was wired. That is the same
defect class as P-PERF-08 (a cache consulted after the syscall it was meant to remove),
and the write-count gates could never see it because a global-variable lock is neither
an object write nor an event-budget phase.

### Fixes
- **P-PERF-19**: the seven macros bind to `GetCachedSymbolStateIndex()`; the five
  per-entry accessors (`GetHistoryEntry`/`SetHistoryEntry`/`ResizeHistory`/
  `GetHistoryArray`/`SetHistoryArray`) use it too; the resolver is instrumented
  (`g_stateResolveLockedCalls` / `g_stateResolveLockedMs`, counted only on a miss so the
  fast path pays nothing) and its cost is printed in the existing breakdown line.
- **P-PERF-19b**: the load window now reports `load=[dedup= fmt= save= restore=]`.
- **P-PERF-19c**: every loop condition that resolved the macro per iteration reads a
  local (`HistoryEntryExists` + the two debug-table builders).
- **P-PERF-20**: `SaveBasePriceHistory()` is called only when `HistoryContentDiffers()`
  says the bytes on disk would change, instead of inferring a change from the counts the
  dedup/migrate passes returned.

## P-PERF-21..22 — family isolation: one switch must touch ONE family — NOT COMMITTED

User's report: "چرا سطوح هی حذف میشه دوباره رسم میشه ... مثلا تریگر روشن میکنی روی سطوح
ساختار چرا اثر داره اینا نباید روی هم اثر بزارن". Reproducible, and it was THREE copies of
one mistake plus a fourth instance of a dead-helper pattern.

### P-PERF-21 — the trigger overlay was wired into the global repair path

The overlay owns exactly ONE family (the trigger ZONES), and the flag is read ONLY by
`RenderZones` (`zones[i].isTrigger && !triggerEnabled`). It was nevertheless:

1. in `levelSig` — the TOPOLOGY signature — so a T press made `levelTopologyChanged` true and
   ran `ClearAllLevels()`: every level line, every zone and every label deleted;
2. raised as `g_forceClearOnNextDraw` at all THREE toggle sites (T hotkey, ring CIR_TRIGGER,
   the TRIGGER card's SHOW row) - which forces the wipe even when the signature agrees;
3. in `PipelineGeometryKey`, so even without the wipe the whole geometry was discarded and
   recomputed to identical output.

Proof it was a false dependency: `CalculateLevels` never reads it, `BuildZonesAndLines` never
reads it, and the two classify helpers that TAKE it as a parameter (`GetPathForLevelOptimized`,
`GetZoneColorForLevel`) never look at it - their own comments say the trigger switch must not
restyle anything.

Fix: the flag moved from the topology signature to the RENDER signature (`frameSig`), the
geometry key dropped it, and all three sites raise only `g_redrawTHLevelsNeeded` (the menu and
card use `REFRESH_BUFFERS` instead of `REFRESH_ALL`, so no label relayout either). A T press is
now one re-render; structure lines/labels/zones are never deleted.

Also closed a hole P-PERF-18 left: the geometry CARRIES zone colours (`ClassifyLevels` stores
`zoneColor` from `GetZoneColorForLevel` / `GetTriggerRenderColor`) but none of their inputs were
in the key - the staleness was masked because every colour edit also changes `levelSig` and
wipes, i.e. the cache relied on a DIFFERENT guard to be correct. The key now proves
`inpShowStructure`, `inpShowStructureL1..L5`, `inpStructureL1..L5Color`, `inpShowMidZones` and
`GetTriggerRenderColor()`.

### P-PERF-22 — the L switch walked the whole chart

`ObjectsTotal(0, -1, -1)` + `ObjectName(0, i, -1, -1)` + `ObjectGetInteger(OBJPROP_TYPE)` for
EVERY object on the chart (ours, other indicators', MT4's own), then an `OBJPROP_TIMEFRAMES`
write per line whether or not the mask had changed. `SetAllLineObjectsVisibility()` in
`Biotak/VisibilityManager.mqh` - the object-cache walk that does exactly this, bounded by
`g_objectCacheSize`, zero `ObjectName` calls, with the P-PERF-02 epoch bump - **existed and had
no callers**. Third instance of the same defect class (after `GetCachedSymbolStateIndex`,
P-PERF-19). The hotkey now calls it, and the hotkey's own exclusions moved INTO the walk so
behaviour is identical: `_B_Top/_B_Bottom/_B_Left/_B_Right` belong to the F switch, `_BK_` trade
rays are never level lines (P-BK-01). Spelled out inline because `IsZoneBoxBorderObject` lives
in `EventHandlers.mqh`, included after `VisibilityManager.mqh`.
