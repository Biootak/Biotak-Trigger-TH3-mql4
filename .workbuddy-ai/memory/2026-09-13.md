## شاهدها (بدون حدس)

1. **از کامپایلر پرسیدیم، نه از حافظه.** MQL4 فقط `#ifdef` دارد (`#if`/`#warning` هیچکدام

   (`switch(0){case CHARTEVENT_X: case 0: ... case 11: break;}`)؛ MetaEditor خودش مقدار تکراری را
   چاپ میکند. نتیجهٔ قطعی:

   تاگل L، کل هندسه را دور میریخت و لیستهای بایتبهبایت یکسان را دوباره میساخت.

1. `RuntimeSettingsSaveOverrides()` wrote all 97 override keys + `GlobalVariablesFlush()` on every

2. The CHART_CHANGE branch initialised its viewport snapshot to 0, so on the FIRST event of every
   instance `viewportChanged` was true by construction → a full `RedrawAllObjects(false)` inside the
   event (the 3.4–4.1 s lines, ×53/day).
3. `g_linesVisible` had four writers and only the L hotkey wrote the object mask. The panel SHOW LINES
   rows and the factory reset set flag+mirror+GV only. P-PERF-25 then made the render skip *provable*

4. Generalised: `frameSig` (a *derived-geometry* signature) was also vetoing the *paint*, while the

  shadow from outliving the keys it describes.
- **P-PERF-28**: `s_ccPrimed` primes the CHART_CHANGE snapshot from the live chart, so the first
  event of an instance is a no-op; added `chart change breakdown: redraw=/labels=/tail=`.
- **P-PERF-29**: one owner for the line-visibility switch — `SetLinesVisible(visible, persist)` sets
  state + mirror + cache + persisted key + MASK; the L hotkey, both panel rows and the factory reset
  all route through it.
- **P-PERF-30**: separated "is the geometry stale" (`frameSig`) from "the user asked for a repaint"

### Honesty note that had to be written into the code
MQL4 has **no threads**: one OS thread, one core per program; `OpenCL` is MQL5-only and a **DLL** is the
only way to create an OS thread. So "add threads" was implemented as **concurrency, not
parallelism** — and the code states plainly that this layer ORDERS and SPACES work; it cannot split a
single frame body (that is the staged pipeline's job: four families, four frames).

### The TF-switch answer — IMPLEMENTED (P-PERF-38/38b/38c/38d)
The three-part design above was carried out, and then a **fourth** part turned out to be the one that
actually mattered: on a period change MT4 RELOADS the indicator, so the new instance starts with an empty
stored signature and the first comparison is trivially "changed" -> `shouldClearLevels` -> full
`ClearAllLevels` of the family the teardown had just kept. Keeping an asset across instances is not
enough; the FACT that it was kept has to be handed over. Now the teardown writes ONE per-chart
fingerprint of the inputs that decide which object NAMES may exist (`AdoptionFingerprint()` — scheme id,
mode, max levels, start point, LS-first, harmonic; never the prices) and `ResolveTopologyAdoption()`
(end of `OnInitHandler`, after the custom-price restore decides `g_thStartPointType`) compares it. On a
match the first pass seeds the stored topology and `ApplyCacheInvalidation` skips the TF force-clear: no
wipe, no staged restart, one in-place property pass. No stamp (first attach / old build / just REMOVEd)
= no adoption = the old behaviour, and every deleting teardown clears the stamp.

### The earlier TF-switch answer (design, before it was implemented)
MT4 **forces** deinit+init on a chart period change (`uninit reason 3` in the log proves it), so the cost
can never be literally zero. What it CAN be made is *no visible churn*, and that needs three things:
1. **TF-independent object names.** Today `objectPrefix = inpObjectPrefix + "_" + currentTFStr + "_"`,
   so every switch orphans one namespace and the new one must be created from scratch.
2. **Adopt what is already on the chart** at init instead of rebuilding (populate the object cache from
   the live objects, then update in place).
3. **Skip the teardown delete on `REASON_CHARTCHANGE`** so the objects survive the switch at all.
→ Resulf: a switch becomes one property-update pass (identical in shape to a single re-render) instead of
delete ~900 + create ~900 + recompute the whole geometry. This is the deliberate next step; it is NOT
done yet because the TF-in-name scheme is load-bearing (cross-TF ghost sweeps in `ClearAllLabels`,
`ClearAllLevels(s_lastPrefix)`, legacy suffixes) and it needs to be done as one coherent change with gates.

### P-PERF-38e — the piece that keeping the family made necessary (found by checking, not by guessing)
Before believing the adoption was safe I checked whether the create path can survive meeting an object it
did not make, and it could not: MT4 refuses `ObjectCreate` for an existing name (error 4200), and
`CreateTHLineObject` (ObjectFunctions.mqh) is the ONE creator in the level/label families that decides
existence from the CACHE rather than a chart probe. Every other site was audited and probes `ObjectFind`
first (ZoneFactory 114-122/330-338, ZoneRenderer 265-273, `CreateLevelLine`, `CreatePipDistanceLabel`,
LabelFunctions 105-130/258-275/424-440, HTF candles 245/375); `ExecuteBatchOperations` has no callers.
So on every adopted frame the High/Low lines would have failed to create, kept the PREVIOUS timeframe's
price, and returned false — abandoning the rest of that function, silently, because the diagnostic is
behind `ENABLE_DEBUG_LOGS`. Fixed by ADOPTING: if `ObjectFind` proves the object is there, write its price
for the new timeframe, let the guarded property writes run unconditionally once, then `CacheUpdateObject`
records the real values so later frames are guarded again.

### P-PERF-40 — the measured cause of "toggles feel slow" was not work at all
The question was "make toggling all levels near-zero everywhere". The log answered it differently
than expected: **45** lines of `owed frame (chart-event) waited=46..266ms body=0ms clear=0`. `body=0ms`
= zero work; `waited` is uniformly up to the 250 ms timer cadence. P-PERF-34 scheduled an in-event
forced frame (its body was 531 ms and it froze the press) but nothing ever DRAINED that debt in the event,
so the press was acknowledged by a repaint of the OLD picture and the real frame arrived up to a quarter
second later. Fix: the drain lives at the event ENTRY POINTS (after `g_inChartEvent = false;`, both .mq4
files — the one place covering both handlers and future paths) and calls `CoopPump()`; the frame runs with
`force_redraw = FALSE`, which is what keeps the event guard meaningful. Its cost is measured and INCLUDED
in the event budget (`settle=`), because a hidden drain is the same defect one level up.

### P-PERF-38f — a cleanup that ran more often than the thing it cleans
`ClearAllLabels` swept 11 legacy `_LBL_` namespaces once per draw generation = on EVERY TF switch: 11
`ObjectsDeleteAll` kernel walks of the whole chart to clear names the timeframe-free scheme can no longer
create and that the one-time migration (P-PERF-38c, superset prefix set) already removes at init. Now keyed
on the migration's OWN stamp: one `GlobalVariableCheck` in steady state. The stamp name moved to ONE owner
(`NameSchemeStampName()` / `LegacyNameSchemeMigrated()` in GlobalVariables) because LabelFunctions is
included BEFORE EventHandlers.

### Also verified (not changed)
`GetTimeframeTH()` → `CalculateTimeframeTH(GetFractalTimeframeForCurrent())` → `ApplyFractalShift(...)` is
**period-dependent**, so level PRICES genuinely differ per timeframe by design. "Zero cost" therefore
means zero destruction + zero irrelevant repeat work, not "don't compute".

### P-UI-40 — «keyboard and panel are out of sync»
Built after a **negative check** rather than a guess: the rows read LIVE globals (`PnlCurrentSet`), so
a VALUE could never differ. The IMAGE could — a switch is an `OBJ_BITMAP_LABEL` whose bitmap only a paint
pass replaces — and every writer INSIDE the panel file repaints its own row, while the panel file is
included AFTER `EventHandlers`, where every hotkey (L, T, A, countdown, TH, step mode, reset, lock) and the
ring's own click handler (ZONES, TRIGGER, ATR, TH) live. So a key press or ring click changed the state,
the chart obeyed, and an open card kept the previous switch position. `PnlSyncOpenStepRow` was the ONLY
sync of this kind that existed — exactly the "some switches work, some don't" shape of the report.
Fix: the same owe/drain pair used for the frame. `RequestUISync()` (GlobalVariables — solves both include
order and Lite's panel-less build) is drained by `UISyncDrain()` (BiotakPanels): consume first, then repair
BOTH layers (ring states+badges, and the open card's rows; item 13 keeps `BkMiniRefresh`). Drained at the
event tail (key and panel in the SAME event, cost reported as `panels=`) and in `RefreshKitOnBar` as the
tick net. The Step card RESHAPES on a mode change, so it keeps its own rebuild owner and the gate refuses
to let that be dropped.

rewritten). `probe-budget-audit` clean with the new **`name-scheme`** (+38e, +38f), **`topology-adoption`**,

## Cycle — P-PERF-41: «مثل دکمه f» (Zones & Levels master + family switch as a mask)

### Report
«درست خاموش و روشن نمیشه مثل دکمه f» + screenshot of the ring with a single line on the chart.

### Root cause, in three layers (all the same shape: one owner making HALF the decision)
1. **The ring item is named "Zones & Levels" and moved only `g_showMidZones`.** Its card
   exposes row 0 = MID ZONES and row 1 = SHOW LINES; the badge, the light and the tooltip
   all read that single flag. So the one control naming the whole family could not switch
   the level LINES off.
2. **OFF was a destruction, not a mask.** `CleanupSurplusPipeline` started its zone walk at
   index 0 when `zonesEnabled` was false → OFF = 7 `ObjectDelete` per zone, ON = `CreateZone`
   + 7 mask writes. F/L have always been one mask per object. The index walk also cannot be
   complete in principle (`maxConsecutiveMiss` stops it).
3. **Two mask writers answering different questions** (only reachable once the family is
   KEPT, i.e. it is created by fix #2): `VisibilityShowAllCached` (F) had no input for the
   zone switch and repainted every non-line object ALL_PERIODS — so "zones off" survived
   until the next F press. It also classified `_Zone_..._Top/_Bottom` as non-lines (the
   `_Zone_` name rule precedes `_Above_`), so F-show re-revealed zone boundary lines with L off.

### Fix (after the revert — see "Reverted" below)
- The ring item keeps ONE switch: `g_showMidZones`. Light, badge, tooltip and click all read
  that one flag. Panel rows 0/1 `RequestUISync()` (repaint only, no state).

### Reverted (and why this is the important part of the cycle)
Layer 1 was first "fixed" by making the ring item a MASTER over both layers
(`ZonesAndLevelsMasterOn()` = `g_showMidZones && g_linesVisible`, click → `SetLinesVisible`).
The user caught the consequence immediately: with zones ON and lines OFF, a press flipped the
master to on and **switched the level lines back ON** — a control silently overwriting another
control's choice. Reverted. **"It feels unreliable" is never fixed by moving MORE state; it is
fixed by moving the right state reliably** — which is layers 2 and 3, and they are the whole of
the performance/consistency fix. The gate now asserts the negative (the CIR_ZONES branch slice
may not touch the line switch or delete anything, and no `ZonesAndLevelsMasterOn` helper may
come back) because the wrong fix is the one most likely to be re-invented.
- `VisibilityZoneMask(nm, zonesVisible, linesVisible)` — ONE predicate, beside the other
  `OBJPROP_TIMEFRAMES` owners in `VisibilityManager`: family switch → boundary-line switch → F mask.
  `VisibilityShowAllCached`/`VisibilityShowAllLegacyScan` take the zone switch as a 5th input.
- `HideAllZoneFamilyObjects(zonesVisible)`: one cache walk over the whole `_Zone_` family,
  guarded writes, plus a change guard keyed on (family, hidden, lines, `g_tfEpoch`) so a
  scroll/zoom in the OFF state sweeps nothing. `RenderZones` enters it before its loop.
- `HideZoneFamilyLegacyScan`: the cold-cache fallback (a TF switch clears the cache but keeps
  the family), latched on `g_drawGeneration`; `ApplyTfMaskGuarded` adopts what it writes.
- Cleanup returns to "remove what this render no longer produces" (`maxLogicalStep + 1`, both
  states) and stays forbidden from being guarded by the flag that turns the family off.

### Considered and REJECTED (recorded so nobody re-litigates it)
- Hiding trigger bands instead of deleting them: a trigger band and a structure band are the
  same `_Zone_` names/shape, so the F show path (which only knows the FAMILY switch) would
  blink them back for the frame between the F press and the render that re-hides them. The
  delete is already free after the first pass (proved-absent cache) and only runs when
  `IsTriggerLevelsEnabled()` moved (it is in frameCore).
- Scheduling a heavy frame from the F key to land the render in the same event: F works today
  and P-PERF-34/40's architecture is exact; the residual it would close was made ~0 by layer 3.

### Gates (all green)
Full + Lite **0 errors / 0 warnings**. `probe-budget-audit` clean; the old `P-PERF-36` sub-check
was REPLACED by the stronger `P-PERF-41` invariant (**`family-isolation` (h) + (h2)**), because

stale seed (`ring stops asking the UI`) was re-anchored to the line it actually asserts.
**118 seeds, all caught.** `write-budget` / `gesture-budget` / `ui-text` / `zorder` / `panel-art-proof` clean.

### Follow-up cycle — P-PERF-41e: THE REAL "IT DOESN'T TOGGLE" CAUSE, AND IT WAS MINE
Report: «خوب چرا درست روشن و خاموش نمیکنه» + screenshot (EURUSD M1, zone bands visible).

**Proven mechanism.** P-PERF-41b (mask instead of delete) was correct, but it carried a
family-level change guard:
`if(zonesVisible == last && hidden == last && lines == last && epoch == last) return 0;`
- Its ONE caller is the render's `if(!config.zonesEnabled)` branch, so `zonesVisible` is a
  **constant false** — the guard cannot see the transition it claims to detect.
- `g_tfEpoch` does NOT move in an off→on→off cycle: the ON render re-shows masks through
  `ApplyTfMaskGuarded`, which by design only caches what it wrote and never bumps the epoch.
  Verified by enumerating every `BumpTfEpoch()` site (init, F hotkey/`HideAll`/`ShowAll`,
  `SetAllTHObjectsVisibility`, `SetAllLineObjectsVisibility`, `CacheRefreshVisibilityState`).

So: press 1 hid the zones, press 2 showed them, **press 3 returned 0 and left them up — and
so did every press after that.** The control was latched dead by an optimisation, not by the
mask.

**Fix.** Family-level latch deleted; the sound guard is per-OBJECT (`ApplyTfMaskGuarded`),
which compares against the mask last written for that name — right granularity, free when that
object is right, structurally capable of seeing every transition because it summarises nothing.
Cost was never a reason for the summary: while off the walk is one hash probe per cached name
and **zero** terminal writes, where the ON render pays eight guarded calls per zone. The walk
also takes **no boolean parameter** now (a constant passed in as an argument reads like a
variable to compare against — that is how the latch was justified), so the mistake is
unwritable rather than merely gated.

**A rival hypothesis was tested and REJECTED before touching anything:** that
`OBJPROP_SELECTABLE = false` on the ring's bitmap labels means `CHARTEVENT_OBJECT_CLICK`
never arrives. The sibling reference project (`../ichimoku`) sets `false` on the same ring
objects, and the user's screenshot shows the ring's TOOLS submenu open — which only opens on a
click of that item. So clicks arrive; the dispatch path was left untouched.

### Falsifiable predictions for the next log
1. A **repeated** ring press must hide and show the zone bands every time — specifically the
   third and later presses, which used to be silently skipped.
2. The ring's Zones & Levels press moves ONLY the zone bands. A line state set elsewhere (the
   L key or the SHOW LINES row) is never changed by it — including the "lines off, zones on"
   combination, where a press must leave the lines off.
2. Turning the family OFF must not produce delete churn: no `CleanupSurplusObjects` zone walk
   in the page, and no create pass when it is turned back on.
3. With zones OFF and F pressed twice, the zone bands must NOT come back.

وقتی دکمه شو زدیم روشن شد و خاموش نمیشه باید خاموش بشه و برگرده به حالت پیش فرض»

## دو باگ، یک شکل
**الف) حالتِ مشتق که از دستِ صاحبش در نمی‌ره.** خط با `SELECTABLE true` **و** `SELECTED true` ساخته می‌شد
(هر سه مسیر جای‌گذاری: کلید C، کلیکِ چارت، دکمهٔ رینگ) و هیچ مسیری آن را پاک نمی‌کرد. MT4 آبجکتِ **SELECTED**
را در **هر درگٍ بعدی در هر جای چارت** جابجا می‌کند — پس خطِ ته‌نشین با درگِ کارت‌های پنل، باکس‌های BaseKnot و
اسلایدرها می‌جنگید و `g_customTHStartPrice` را بی‌اطلاع کاربر عوض می‌کرد. (انتخابِ خودکار هم لازم نبود:
MT4 خودش یک SELECTABLE را در همان فشاری که گرفته می‌شود انتخاب می‌کند.)
**ب) خروجی که یک‌طرفه بود.** دکمهٔ PIN رینگ هر بار فقط **دوباره آرم** می‌کرد (حذف خط + ساخت مجدد روی قیمت
بازار + انتخاب مجدد) پس چراغ روشن می‌شد و خاموش نمی‌شد؛ خروجِ واقعی فقط در ESC بود و **inline** نوشته شده بود،
یعنی دکمه حتی امکانش را هم نداشت.

## کارها
- `CreateCustomPriceLine(price, digits, editable=false, suffix)` — پارامتر به «حالت تعامل» تبدیل شد:
  `true` = جای‌گذاری/تنظیم (SELECTABLE، هرگز SELECTED) و `false` = **ته‌نشین/بی‌اثر** (هیچ‌کدام).
  مسیرهای restore و هر دو مسیر تأیید (double-click) حالا با همین مالک ساخته/ته‌نشین می‌شوند.
- `g_customPriceNativeDrag` — انتخابِ باقی‌ماندهٔ یک گِسچر دقیقاً **یک‌بار** در button-up پاک می‌شود؛
  latch را هندلرِ OBJECT_DRAG و شاخهِ کلیکِ تک می‌گذارند و هندلرِ درگ آن را پاک **نمی‌کند** (آن رویداد در
  طول درگ پیوسته است و پاک‌کردنش خط را از دست کاربر می‌کشد). هزینه: یک read بولی به‌ازای هر mousemove،
  یک ObjectSetInteger به‌ازای هر گِسچر.
- `DeactivateCustomPriceMode(src)` — تک‌مالکِ «خروج» (خط + GVarها + `g_thStartPointType = inpTHStartPointType`
  + بیلد اجباری که با گاردِ P-PERF-34 به فریم واگذار می‌شود). ESC و فشارِ OFF دکمهٔ PIN هر دو همین را صدا می‌زنند
  و دکمه حالا **toggle** واقعی است.
- تولتیپ‌ها راست می‌گویند: در حالت قابل‌ویرایش «Drag to adjust, Double-click to confirm» و در حالت ته‌نشین
  «PIN button to move».

## تأیید
- Full: **۰ خطا / ۰ هشدار** (هر دو `.ex4` بازنویسی شد؛ Lite این ماژول‌ها را include می‌کند ⇒ همان بیلد).
- گیتِ جدید `probe-budget-audit custom-price-mode` (۵ invariant: تک‌مالکِ خروج + مسیر ESC از آن، هر دو جهت دکمه،
  پیروی سازنده از حالتش، هیچ سایتی pre-select نکند، پاک‌شدن مؤخرِ انتخاب) + **۶ seed** ⇒ سلف‌تست **۱۳۴/۱۳۴**.
- `write` / `gesture` / `ui-text` / `zorder` تمیز.

## باز مانده / ریسک شناخته‌شده
- بعد از تأیید، خط دیگر SELECTABLE نیست ⇒ «درگ برای تنظیم» فقط در حالتِ جای‌گذاری (فشار روی دکمهٔ PIN) ممکن است.
  این دقیقاً همان چیزی است که تداخل را حذف می‌کند؛ اگر کاربر بخواهد خطِ ته‌نشین را بدون re-arm هم بکشد، باید یک

  همان مقدار، «حالت پیش‌فرض» است؛ رفتار با ESC یکی است و عمداً تغییر نکرد.

# چرخهٔ P-UI-48 — «خط کاستوم پرایس مثل قدیم حرکت کنه، ولی مشکلاتش رفع بشه»

## گزارش
«طوری درستش کن که به پرفورمنس و رفتار اندیکاتور تغییر نیاد … خط کاستوم پرایس چرا مثلا
قدیم حرکت نمیکنه باید مثل قدیم حرکت بکنه ولی مشکلاتش رفع بشه.»

## ریشهٔ رگرسیون (P-UI-45 نصفه بود)
P-UI-45 گزارش «خط با پنل‌ها/آبجکت‌ها می‌جنگد» را به «خط نباید SELECTABLE باشد» ترجمه کرد؛
اما SELECTABLE **خودِ درگ** است. مکانیزمِ تداخل فقط `OBJPROP_SELECTED` بود که ماندگار
می‌شد (کدِ قدیمی در لحظهٔ ساخت `true` می‌نوشت، پس **پیش از هر گِسچر** ست بود) و MT4 آبجکتِ
SELECTED را در هر درگِ بعدی در هر جای چارت جابه‌جا می‌کند. نتیجهٔ ترجمهٔ اشتباه: خط
ته‌نشین قابلِ‌گرفتن نبود، کشیده نمی‌شد، و double-click (تأیید SS/LS + تولتیپ) هم با
همان پرچم از دست رفت.

## کارها
- **یک سازنده**: `CreateCustomPriceLine(price, digits, tooltip)` همیشه `SELECTABLE true`
  + `SELECTED false`؛ و **هر پنج** مسیر ساخت (کلید C، کلیک چارت، بازگردانی TF Lock،
  دکمهٔ PIN رینگ، هلپر) از آن رد می‌شوند. سه بلوکِ دست‌نویس (که هرکدام کلِ مجموعهٔ
  پراپرتی‌ها را تکرار می‌کردند) حذف شد.
- **یک مالکِ پاک‌کردن**: `ClearCustomPriceSelection()` (خواندنِ گارددار + یک نوشتن) و چهار
  تریگر: (a) لچِ `g_customPriceNativeDrag` در button-up ماوس‌مُو، (b) فاینالایزرِ
  `ChartPointerFinalizeOnUps` (رهاشدنِ بی‌حرکت هیچ رویدادِ مُؤی نمی‌فرستد - تلهٔ
  P-BK-03)، (c) گاردِ فشار در `HandleUIChartEvent`:
  `if(pressStart && g_DragOwner != DRAG_NONE) ClearCustomPriceSelection();`
  (d) **درگِ بومیِ هر آبجکتی که خودِ خط نیست** در همان `CHARTEVENT_OBJECT_DRAG`:
  `if(sparam != g_customPriceHorizontalLineName) ClearCustomPriceSelection();` —
  باکس‌های Base/Knot هم هندلِ درگشان `SELECTABLE` است و MT4 **هر** آبجکتِ SELECTED را
  حرکت می‌دهد؛ پس درگِ باکس، خط را هم می‌کشید. ریسکی که در نسخهٔ قبلی باز مانده بود،
  همین بود و با همین مقایسهٔ رشته بسته شد.
- **تولتیپ راست**: همهٔ حالت‌ها کشیدنی‌اند ⇒ متنِ ثابت «Drag to adjust, Double-click to
  confirm» (متنِ «PIN button to move» دروغ شده بود).
- **پرفورمنس**: صفر کارِ جدید در فریم. درگ همان درگِ بومیِ MT4 است، پس throttle و
  `g_customPriceLineDragging` (استثنای P-PERF-34) و مسیر live-update دست‌نخورده‌اند.
  هزینه: خواندنِ بولیِ قبلی در مسیر مُو، یک خواندنِ گارد‌دار در هر button-up، و حداکثر
  یک نوشتنِ پراپرتی در هر گِسچر.

## تأیید
- Full و Lite هر دو **۰ خطا / ۰ هشدار**؛ `Biotak_PanelFlow_Test.mq4` هم بازسازی شد.
- گیتِ `probe-budget-audit custom-price-mode` بازنویسی شد: سازنده باید خط را **قابل‌گرفتن**
  نگه دارد، `SELECTABLE` فقط در **یک** جا و `SELECTED, false` فقط در **دو** جا نوشته شود،
  و مالکِ پاک‌کردن از هر سه تریگر قابلِ‌دسترس باشد. **۱۴۲ seed، همه گرفته شد**.
- `write` / `gesture` / `ui-text` / `zorder` تمیز.

## باز مانده (ریسکِ شناخته‌شده، نه باگ)
- فشارِ همزمان روی **باکسِ Base/Knot** و خطِ کاستوم پرایس بسته شد (تریمگرِ (d) بالا).
  باقی‌مانده فقط این است که اگر MT4 بر اثر برخوردِ z-order باکس را نه، بلکه خط را انتخاب
  کند، درگِ آن گِسچر به خط می‌رود - که رفتارِ موردِانتظارِ کاربر هم هست (روی خط فشار
  آمده).

# چرخهٔ P-UI-49 — «خط کاستوم پرایس رو نمیشه درگش کرد مشکل چیه»

## گزارش
«طوری درستش کن که به پروفورمنس و رفتار اندیکاتور تغییر نیاد. خط کاستوم پرایس رو نمیشه
درگش کرد مشکل چیه.» (بعد از P-UI-48: پرچم‌های SELECTABLE/SELECTED درست شده بودند، ولی
درگ هنوز خط را حرکت نمی‌داد.)

## ریشهٔ واقعی (قانونی که خودمان نقضش می‌کردیم)
P-UI-48 حرکت را از «انتخابِ دائمی» به «درگِ بومیِ per-object» منتقل کرد. آن درگ یک گِسچرِ
**زنده** است که MT4 مالکش است، و قانونِ همان گِسچر از قبل در همین مخزن ثبت شده بود —
P-BK-15: «MT4 درگِ در جریان را وقتی آبجکتِ درگ‌شده به‌صورت برنامه‌ای بازنویسی شود لغو
می‌کند» (و همان قانون در followِ خانوادهٔ سطوح: «هرگز Sync کامل در هر استپ — بازنویسیِ
style/tooltip بچه‌ها را از باکسِ بومی عقب می‌انداخت»).
هندلرِ `CHARTEVENT_OBJECT_DRAG` خط در **هر استپ** تولتیپِ خط را می‌نوشت (متن شامل قیمت
است ⇒ همیشه متفاوت ⇒ نوشتنِ واقعی). با خطِ پیش‌انتخاب‌شده این نوشتن نامرئی بود، چون حرکت
از **انتخاب** می‌آمد؛ با درگِ per-object همان نوشتن گِسچرِ خودش را کشت.

## کارها
- مالکِ واحدِ متنِ تولتیپ: `UpdateCustomPriceTooltip()` (تنها `ObjectSetString` روی خط)،
  که از **رها شدن** صدا زده می‌شود: شاخهٔ button-up همان هندلرِ ماوس‌مُوی درگ، **بعد** از
  فریم (`RedrawAllObjects` + `ThrottledChartRedraw`).
- هندلرِ درگِ خط فقط **می‌خواند** و وضعیت را می‌نویسد (قیمت، GVars، start point، override،
  فریمِ live). صفر نوشتنِ پراپرتی روی خط در حینِ فشارِ دکمه.
- بقیهٔ مسیر گِسچر بررسی شد: بلوکِ custom-price در redraw با `g_customPriceLineDragging`
  رد می‌شود و شاخه‌های دیگرش (override موجود / آبجکت گم‌شده) نوشتنی ندارند؛
  `PnlHandleDrag` برای نامِ ناشناخته `REFRESH_NONE` برمی‌گرداند.

## تأیید
- Full / Installed / Lite: **۰ خطا / ۰ هشدار** (هر دو `.ex4` بازنویسی شدند).
- گیتِ `probe-budget-audit custom-price-mode`: بدنهٔ درگِ خط نباید `ObjectSet*` روی خط
  داشته باشد + تولتیپ یک مالک + مالک از مسیرِ رها شدن؛ **۱۴۵ seed، همه گرفته شد**
  (۲ seed جدید).
- `write` / `gesture` / `ui-text` / `zorder` تمیز.
- هزینه: یک نوشتن در هر گِسچر **به‌جای** یک نوشتن در هر استپِ درگ ⇒ کمتر از قبل، بدونِ
  کارِ جدید در فریم.

## P-UI-49b — گزارش دوم: «حالت درگ خیلی سریع قطع می‌شه»
«حالت درگ خط کاستوم پرایس خیلی سریع قطع میشه نمیشه درگ کرد قابل سلکت بودنش» — یعنی بعد از
P-UI-49 درگ **شروع** می‌شود و در همان گِسچر می‌میرد (گزارش قبلی: اصلاً شروع نمی‌شد).

**ریشه:** فاینالایزرِ `ChartPointerFinalizeOnUps()` (پنل‌ها) انتخابِ خط را **inline** پاک
می‌کرد، و این فاینالایزر از `CHARTEVENT_CLICK` و `CHARTEVENT_OBJECT_CLICK` صدا زده می‌شود —
که یکی‌شان روی **همان فشارِ** گرفتنِ آبجکتِ SELECTABLE می‌آید (MT4 اول آبجکت را انتخاب می‌کند،
بعد رویدادِ همان فشار را به اندیکاتور می‌دهد). هندلرِ کلیکِ دامنه برای همین خطر پاک‌کردن را
موکول کرده بود (`g_customPriceNativeDrag` را arm می‌کند و پراپرتی نمی‌نویسد) — و فاینالایزر،
که یک چرخهٔ بعد در همان رفع اضافه شد، در **همان رویداد** انجامش داد. پس انتخابِ MT4 وسطِ
همان فشار پاک شد و درگ همان‌جا مرد.

**کار:** فاینالایزر حالا latch را **arm** می‌کند (یک bool store) به‌جای پاک‌کردنِ inline؛
پاک‌شدن همان‌طور که P-UI-45 طراحی کرده بود، در نخستین ماوس‌مُویِ دکمه‌بالا و از مالکِ واحد
(`ClearCustomPriceSelection`) انجام می‌شود. تریگرهای دیگر (button-up، گاردِ فشارِ UI، و
درگِ بومیِ آبجکتِ بیگانه) دست‌نخورده‌اند. هزینه: کمتر از قبل (bool store به‌جای خواندنِ
گارد‌دار + نوشتنِ پراپرتی)، صفر کارِ فریم.

**تأیید:** گیتِ `custom-price-mode` حالا فاینالایزر را دو طرفه می‌سنجد (نه `ClearCustomPriceSelection()`
و حتماً خطِ arm) + ۲ seed ⇒ **۱۴۶/۱۴۶**؛ Full / Installed / Lite صفر خطا صفر هشدار؛
`write` / `gesture` / `ui-text` / `zorder` تمیز.

## باز مانده (ریسکِ شناخته‌شده، نه باگ)
- P-BK-16 روی همان باکس‌ها نشان داد MT4 گاهی قفل می‌کند و درگِ بومی هیچ‌وقت engage نمی‌شود.
  اگر کاربر همان «حرکت نمی‌کند» را دوباره دید، قدمِ بعدی همان fallbackِ P-BK-16 برای این
  خط است (حرکتِ absolute از نقطهٔ فشار، توسط خودِ ما) — نه دست‌زدن به پرچم‌ها.
- USER ACTION: Remove & Re-Add اندیکاتور (MT4 هیچ‌وقت `.ex4` جایگزین‌شده را hot-swap نمی‌کند).

# چرخهٔ P-UI-51 — «حالت درگ خیلی سریع قطع میشه» (گزارش سوم)

## گزارش
«طوری درستش کن که به پروفورمنس و رفتار اندیکاتور تغییر نیاد. حالت درگ خط کاستوم پرایس خیلی
سریع قطع میشه نمیشه درگ کرد قابل سلکت بودنش.» (بعد از P-UI-49 و P-UI-49b: درگ هنوز در همان
گِسچر می‌مرد.)

## ریشه — سه نوشتنِ خودمان، در سه مسیر، هر سه داخلِ گِسچرِ زنده
۱. هندلرِ `CHARTEVENT_OBJECT_DRAG` خط (که MT4 در **هر استپ** می‌فرستد) پرچمِ
   `g_customPriceLineDragging` را صفر می‌کرد. آن پرچم یعنی «تصمیمِ گِسچر گرفته شده، این گِسچر
   مالِ من است»؛ با صفرشدن در هر استپ، بلوکِ grab در مسیر ماوس‌مُوی در هر استپ دوباره اجرا
   می‌شد و مرجعِ carry (`s_ownGrabPrice`) را به قیمتِ **کنونیِ** خط re-arm می‌کرد. آن‌وقت تستِ
   «یخ‌زده» (`|linePrice - ref| < نصفِ پوینت`، شکلِ P-BK-16) قیمت را با خودش مقایسه می‌کرد،
   همیشه می‌گذشت، و carry وسطِ همان درگِ MT4 یک `OBJPROP_PRICE` تازه روی خط می‌نوشت
   ⇒ قانونِ P-BK-15 ⇒ لغوِ درگ و برگشتِ خط به نقطهٔ شروع («خیلی سریع قطع می‌شه»).
۲. شاخهٔ «فشاری که مالِ ما نیست» در لبهٔ فشار، انتخاب را **inline** پاک می‌کرد. آن هیِت‌تست روی
   نخستین **MOVE** بعد از فشار اجرا می‌شود (چند پیکسل دورتر، و هرچه درگ سریع‌تر شروع شود
   دورتر)، پس می‌تواند فشاری را که ترمینال **واقعاً** گرفته از دست بدهد؛ و
   `ClearCustomPriceSelection` فقط وقتی می‌نویسد که `OBJPROP_SELECTED` true باشد — یعنی دقیقاً
   وقتی ترمینال خط را در دست دارد. پس همان نوشتن، انتخابِ MT4 را از درگی که همان فشار شروع
   کرده بود بیرون انداخت.
۳. خودِ carry می‌توانست روی حرکتِ خودِ لبهٔ فشار بنویسد؛ همان یک رویدادی که تستِ یخ‌زده در آن
   بی‌معنی است (قیمت به‌تعریف با قیمتِ لحظهٔ grab برابر است، چه ترمینال بخواهد حرکتش دهد چه هرگز).

## کارها
- پرچمِ گِسچر مالِ لبهٔ فشار و button-up است؛ هندلرِ درگِ خط هیچ‌وقت آن را صفر نمی‌کند ⇒ carry
  همان لحظه که ترمینال خودش خط را حرکت دهد کنار می‌کشد.
- چون پرچم در کلِ درگ روشن می‌ماند، فریمِ اجباری در هندلرِ درگ **inline** اجرا می‌شود (معافیتِ
  P-PERF-34)، پس همان کانال حالا بودجهٔ ۵۰ms مسیرِ ماوس‌مُوی را شریک می‌شود: یک فریم در هر
  پنجره در کلِ دو کانال — همان کادنسِ قبلی و کارِ کمتر در هر استپ.
- فشارِ ناشناخته latch را arm می‌کند (یک bool) و پاک‌شدن مثل قبل در button-up و از مالکِ واحد
  انجام می‌شود؛ carry روی حرکتِ لبهٔ فشار اجرا نمی‌شود (`!pressEdge`) و absolute از کرسر است.

## تأیید
- Full (Workspace) / Installed / Lite: **۰ خطا / ۰ هشدار**.
- `probe-budget-audit` `custom-price-mode` پاک و **۱۵۳/۱۵۳** بذر (۴ بذر جدید؛ یک بذرِ کهنه که
  به خطِ creator قبل از بازنویسیِ P-UI-50 لنگر انداخته بود حذف شد — همان ناوردایی هنوز با
  بذرِ جانشینش پوشش داده می‌شود).
- `write` / `gesture` / `ui-text` / `zorder` تمیز.

## درس
**«یک پرچمِ گِسچر باید یک مالکِ رویدادی داشته باشد.»** اگر رویدادی که در هر استپ می‌آید همان
پرچمی را صفر کند که لبهٔ فشار set می‌کند، هر منطقی که به آن پرچم تکیه کرده باشد (اینجا:
تستِ یخ‌زدهٔ carry) بی‌صدا بی‌اثر می‌شود — و نتیجه‌اش نوشتن روی آبجکتی است که ترمینال دارد
می‌کشد.

# چرخهٔ P-UI-52 — «سطوح لایو همراه خط جابجا نمیشن» + یک چکلیستِ سختسازی

## گزارش
«حالت درگ خط کاستوم پرایس چرا مثل قدیم همراهش بقیه سطوح لایو جابجا نمیشه بدون هزینه و
محاسبات آخر حساب میشد؟ قدیم اینطوری بود.» به‌همراه یک چک‌لیست هشت‌محوره (کلیک‌بلیت،
ماوس‌مووی، درگِ نرمِ پنل، DPI/4K، z-order، minimize، CHART_CHANGE، edit-box، ورودیِ
صفر/منفی، کش، نشتی، پاک‌سازی، Digits/Point، آلرت).

## ریشه (دو علتِ مستقل، یک گزارش)
۱. **قیمتِ start point در امضای هندسه نبود.** start point فقط با **نوعش** (`levelSig`) و
   `g_dailyClosePriceForTH` وارد `frameCore` می‌شد، در حالی که در حالتِ custom-price خودِ
   `g_customTHStartPrice` مرکزِ خط لوله است (`GetMidpointPrice` → `data.midpointPrice` →
   `ExecutePipeline` → `PipelineGeometryKey.centerPrice`). پس حرکتِ خط هندسه را عوض می‌کرد
   ولی `frameSig` **برابر** می‌ماند ⇒ `geometryChanged=false` ⇒ `DrawLevelsBasedOnMode`
   هیچ‌وقت صدا زده نمی‌شد و خانواده فقط با فلیپ‌شدنِ **پرچمِ درگ** (یک‌بار شروع، یک‌بار پایان)
   به‌روز می‌شد.
۲. **هندلرِ درگِ خط در هر استپ wipe می‌خواست.** `g_forceClearOnNextDraw` = `ClearAllLevels`
   + بازسازیِ چهارمرحله‌ایِ ~۹۰۰ آبجکت، و آن هندلر آن را در **هر** استپِ درگ set می‌کرد ⇒
   خانواده پلک می‌زد و از خطی که یک پیکسل جابجا شده بود عقب می‌ماند.
۳. (از چک‌لیست) سه محلِ نمایشِ pip قانونِ `point * 10` را هاردکد کرده بودند، در حالی که مالکِ
   واحدِ پروژه (`GetCachedPipSize()`) برای ۲رقمی‌های غیرفلزی «pip = ۱ point» می‌گوید ⇒
   روی شاخص/کریپتوِ ۲رقمی اعدادِ لیبل ۱۰ برابر کوچک‌تر از بقیهٔ pipهای همان نماد بود.

## کارها
- قیمتِ start point فقط وقتی start pointِ **فعال** است به `frameCore` اضافه شد (quantised با
  digits چارت) ⇒ followِ لایو در همان بودجهٔ ۵۰ms و بدون هیچ کارِ اضافه در بقیهٔ حالت‌ها.
- wipeِ هر استپ حذف شد: followِ لایو = re-assertِ درجا با همان نام‌ها؛ settleِ نهایی همان
  مسیرِ button-up است (force-clear + rebuildِ مرحله‌ای).
- سه محلِ pip به مالکِ واحد وصل شدند (fallback = همان مقدارِ قدیم اگر pip صفر باشد).

## تأیید
- Full (Workspace) / Installed / Lite: **۰ خطا / ۰ هشدار** (لاگ‌ها صفر error/warning).
- `probe-budget-audit` پاک + **۱۵۳/۱۵۳**؛ `write` / `gesture` / `ui-text` / `zorder` تمیز.

## P-UI-53 — «حالت درگ باید چارت پشت قفل باشه»

گزارش: «موقع درگ و کشیدن مشکل اسکرول پیش نیاد». حرکتِ خط درگِ بومیِ MT4 است و
`CHART_MOUSE_SCROLL` به‌طور پیش‌فرض روشن است؛ لایهٔ دامین هیچ قفلی نداشت (قفلِ refcountیِ UI در
ماژولی است که **بعد** از دامین include می‌شود و در Lite وجود ندارد). BaseKnot همین را حل کرده
بود (`BaseKnotLockChart` + P-BK-14 با Chart* خام برای Lite).

کارها (همان قفل، همان شکل، در همان لایهٔ دامین): `CustomPriceDragLockOn()` در grab (با ذخیرهٔ
MOUSE_SCROLL/CONTEXT_MENU/AUTOSCROLL کاربر)، `CustomPriceDragReassertLock()` روی همان بودجهٔ
۵۰ms درگ (read-guarded، طبق P-BK-14)، `CustomPriceDragLockOff()` در رهایش، و
`CustomPriceDragHealStale()` به‌عنوان تورِ رهایشی که ماوس‌مُوی نمی‌دهد (تلهٔ P-BK-03؛ یک bool
read در هر تیک، KEYSTATE فقط وقتی قفل در دست است)، رهایش بی‌قید در `OnDeinitHandler`، و
`ChartLockIntended()` حالا درگِ خط را می‌شناسد تا reconcile زیرِ گِسچر قفل را بر ندارد.
AUTOSCROLL هم در طول گِسچر پایین نگه داشته می‌شود (تیک می‌تواند مقیاس را زیر خط بلغزاند).

تأیید: Full/Installed/Lite **۰ خطا/۰ هشدار**؛ `probe` پاک + **۱۵۶/۱۵۶** بذر (۳ بذر جدید:
برداشتنِ lock/taker، برداشتنِ reassert، برداشتنِ probe کلید).

## P-UI-54 — «خط کلیک میشه همهٔ سطوح از نو میاد، فلیکر داره»

گزارش: «خط کاستوم پرایس کلیک میشه همه سطوح از نو میاد روی چارت فلیکر‌کر داره که نباید باشه،
بهترین راه چیه؟»

**ریشه:** شاخهٔ رهایشِ درگ، `g_forceClearOnNextDraw` را **بی‌قید** set می‌کرد. MT4 خط را روی
همان فشارِ کلیک SELECT می‌کند، پس مسیرِ درگِ ما برای یک **کلیک ساده** هم engage می‌شد و
settleیی که اجرا می‌کرد مسیرِ **wipe** بود: `ClearAllLevels` + بازسازیِ چهارمرحله‌ایِ ~۹۰۰
آبجکت ⇒ فلیکر، برای گِسچری که **هیچ چیزی را جابجا نکرده بود**.

**قاعده:** wipe جوابِ تغییرِ **توپولوژی** است (نوعِ start point، mode، تایم‌فریم — همه در
`levelSig`)، نه تغییرِ **قیمت**. قیمت هندسه است، و از P-UI-52 امضای هندسه خودِ start priceِ
فعال را دارد، پس re-assertِ درجا همان تصویرِ جابجاشده را می‌کشد.

**کار:** رهایش فقط یک سؤال می‌پرسد: «آیا این گِسچر خط را جابجا کرد؟» و اگر نه، **هیچ فریمی**
طلبکار نیست (نه رندر، نه حذف). مسیرِ تأییدِ دابل‌کلیک clear خود را نگه می‌دارد، چون واقعاً
`g_thStartPointType` را عوض می‌کند. هزینه: کلیک روی خط = یک نوشتنِ تولتیپ و صفر فریمِ
ترمینال؛ درگِ واقعی = یک رندر در هر ۵۰ms و صفر حذف.

**تأیید:** Full/Installed/Lite **۰ خطا/۰ هشدار**؛ `probe` پاک + **۱۵۸/۱۵۸** بذر (۲ بذر جدید).

## P-UI-55 — «کلیک می‌کنم، سطوح جابه‌جا می‌شن» (باگ مخفی)

گزارش + دو اسکرین‌شات: خودِ خط در تصویر اول **1.15697** و بعد از یک کلیکِ ساده در تصویر دوم
**1.15705** — ۸ پوینت روی چارت ۵رقمی ≈ **۱.۶ پیکسل** = همان تلورانسِ هیِت‌تست.

**ریشه:** `carry` خودمان نویسنده بود: **absolute به کرسر** بود و روی **هر** ماوس‌مُویِ
دکمه‌پایین بعد از لبهٔ فشار اجرا می‌شد؛ پس جیترِ یک‌پیکسلیِ یک کلیک کافی بود تا قیمتِ زیر کرسر
روی خط نوشته شود. فشار ~۲ پیکسل کنارِ خط افتاده بود (همان چیزی که هیِت‌تست به‌عمد قبول می‌کند)
و آن آفست روی **قیمت** کپی شد ⇒ کاربر واقعاً چیزی را جابجا نکرده بود ولی قیمتِ خط عوض شد و
هر سطحی که از آن مشتق می‌شود با آن جابجا شد. دو نصفِ ماجرا هر کدام تنها "منطقی" بودند؛
با هم یک کلیک را به یک ویرایشِ قیمت تبدیل کردند.

**کار:** همان دو قاعدهٔ باکسِ BaseKnot:
- **SLOP** روی Y (خط افقی افقی جابجا نمی‌شود) نسبت به پیکسلِ لحظهٔ grab ⇒ جیترِ کلیک هرگز
  این در را باز نمی‌کند و کلیک صادق است: قیمتِ خط **اصلاً** عوض نمی‌شود.
- **DELTA**: نوشتن = قیمتِ grab + **طیِ مسیرِ** کرسر از لحظهٔ grab (نه قیمتِ کرسر) ⇒ آفستِ فشار
  حفظ می‌شود و خط هرگز روی کرسر نمی‌پرد.
- هر دو یک **latch فشار** می‌خواهند (`s_ownGrabX/Y` + قیمتِ زیر آن پیکسل)، یک‌بار در هر گِسچر و
  نه در هر حرکت.

**تأیید:** Full/Installed/Lite **۰ خطا/۰ هشدار**؛ `probe` پاک + **۱۶۰/۱۶۰** بذر (۳ بذر جدید)؛
`write`/`gesture`/`ui-text`/`zorder` تمیز.

**درس:** «هر نوشتنی که مقدارش از **کرسر** می‌آید، باید با **حرکت** گیت شود.» یک کلیک هم
حرکتِ یک‌پیکسلی دارد؛ تفاوتِ کلیک و درگ فقط **فاصله** است، نه وجودِ رویداد.

## باقی‌ماندهٔ چک‌لیست (شناسایی‌شده، بدون ادعای پوشش)
- مواردی که گیتِ مستقل دارند (DPI/ui-text، z-order، کلیک/گِسچر، پرفورمنس/hot-path، پاک‌سازیِ
  prefix-base، آلرت‌گاورنر، clampِ موقعیتِ پنل در ownerِ رسم) در گزارش مستند شدند.
- موارد باز که یک چرخهٔ مستقل می‌خواهند: بلیتِ کلیکِ چارت روی آبجکت‌های خودمان در حالتِ
  placement (نیاز به هیِت‌تستِ قطعیِ UI)، و سخت‌سازیِ NaN/Zero-divide (هیچ `MathIsValidNumber`
  در مخزن نیست؛ اعتبارسنجی فعلی range-base است).

## گزارش کاربر

## چرخهٔ P-UI-62 — «تصویرِ زون» دو بیت دارد، و اسلاتِ مرده یک شیء نیست

گزارش کاربر: «empy درست کار نمیکنه» + «به جای هیدن یک دکمه دیگه بزار … یک حالت دیگه
بزا رکه هردو بشه تنظیم کرد هم خط و هر رنگ رو».

**سه چهرهٔ یک نقص:**
۱. اسلاتِ سومِ `ENUM_ZONE_STYLE` برابر `ZONE_STYLE_HIDDEN` بود: یک مقدارِ استایل که
   کلِ خانوادهٔ زون را حذف میکرد = همان سؤالی که سوئیچِ MID ZONES جواب میدهد.
۲. تصویر یک بیت بود (`filled`) و لبه دقیقاً `!filled` ⇒ `false` دو معنا داشت؛
   OUTLINED غیرقابلِبیان بود و BORDER/BORDER WIDTH روی هیچی اثر نمیکرد.
۳. مسیرِ EMPTY **بالای** خواندنِ کش `return` میکرد ⇒ مهاجرتِ پاکسازیِ مستطیل
   غیرقابلدسترس بود. کش هم بدترش میکرد: EMPTY کش نمیشد و هر فریم ۳ آبجکت میساخت.

**کارِ انجامشده:** اسلاتِ سوم = `ZONE_STYLE_BOX_OUTLINED` (تصویر)، دو بیتِ مستقل،
حلِ تصویر پیش از هر مسیرِ رسم، مهاجرت روی تغییرِ KIND، ساختِ باند **قبل** از لبه
(با ZORDER برابر، ترتیبِ نقاشی = ترتیبِ ساخت)، کشِ دوبیت + «آیا مستطیل دارد»،
همهٔ producerها هر دو نیمه را ست میکنند، و شاخههای HIDDEN از همهٔ ماژولها حذف شدند.
مهاجرتِ یکبارهٔ `MZ=2` (zones off + FILLED) با مهرِ `MZ2` و نوشتنِ مقدارِ اصلاحشده
روی دیسک در همان لحظه.

**جستوجوی وابستگی (خواستهٔ صریح کاربر):** `CacheUpdateZone(..., existsOnChart)` حالا
میتواند `exists=false` کش کند ⇒ `CacheSlotIsLive(i)` جلوی هر ۵ walkِ دیدهشدن و walkِ
رنگآمیزیِ ساختار را گرفت؛ ساختِ باند `CacheForgetAbsent` میزند؛ و
`DeleteIndicatorObjectManaged` حالا واقعاً cacheِ اصلی را قبل از علامتِ منفی میخواند.

**گیت:** گروه تازهٔ `zone-picture` (۶ اینواریانت + ۱۴ seed) ⇒ سلفتست **۱۸۹/۱۸۹**؛
`write` ۴۱/۴۱ · `gesture` ۱۸/۱۸ · `ui-text` ۹/۹ · `zorder` ۹/۹ · سیم ۹۶/۱۲۰/۱۴۴ تمیز؛
کامپایل Full + Lite هر دو ۰ خطا. یک seedِ قدیمی («delete probes a proved-absent name»)
با جابهجاییِ ترتیبِ کد stale شد و به شکلِ جدید منتقل شد.

**کارِ کاربر:** MT4 فایل `.ex4` را hot-swap نمیکند ⇒ Remove & Re-Add.

## چرخهٔ P-UI-63/64 — شفافیتِ مستقلِ لبه، و لبه‌ای که خودِ مرزِ زون است
