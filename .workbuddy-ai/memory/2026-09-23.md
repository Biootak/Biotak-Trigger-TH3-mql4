**VERDICT: `CHART_CONTEXT_MENU = false` does NOT remove this MT4 build's right-click menu.**

### The harness (kept, so this cannot be re-argued)

- `_ctxmenu-test.ps1` — `-Action probe | switch -Want "<SYM>,<TF>" | test -X n -Y n`.
  `switch` cycles charts with Ctrl+Tab and verifies the result against the window title
  (never blind tab clicking). `test` right-clicks and reports TWO oracles: a visible
  `#32768` popup owned by `terminal.exe`, and a bright-pixel count of the region where a
  menu paints. It Escapes afterwards.
- `_ctxmenu-probe.ps1` — screens/coords/window-under-point, plus `-Action scan`: finds

  60 px run), which is how the object under the cursor can be named instead of guessed.

### TWO FALSE NEGATIVES, AND THE GUARDS THAT KILLED THEM

A synthetic right-click is not a hardware click, and "NO MENU" is the quietest wrong
answer there is. Both traps were hit and both are now refused inside the harness:

1. **the click went to ANOTHER WINDOW.** `mouse_event` delivers to whatever window is
   under the cursor, and the Freebuff window sat over the test point — so the run reported
   "no menu" while MT4 had never been touched. GUARD: `WindowFromPoint(x,y)` must return
   the terminal's pid AND class `AfxFrameOrView*`, else the run ABORTS (exit 2).
2. **the terminal was not FOREGROUND.** Windows refuses `SetForegroundWindow` from a
   background process, and with MT4 inactive the injected right-click opened nothing —
   a false negative that looks exactly like success. GUARD: activate through
   `AttachThreadInput` + `BringWindowToTop` + `SetForegroundWindow`, then POLL
   `GetForegroundWindow` until it equals the terminal, else ABORT (exit 3).

THE CONTROL IS NOT OPTIONAL: a chart whose property is ON (`EURUSD,Monthly` — the
indicator never touched it) must produce a menu. It does:
`popup pid=9980 rect=(1100,162)-(1306,815) size=206x653`.

## P-UI-102 — THE FIRST LIVE RUN, AND THE THREE THINGS IT PROVED

The user attached the new build and reported «مال متاتریدر هم میاد که مگه نباید با
کنترل باشه». The log answered it with three findings, all fixed in the same hour:

- **A. THE GATE READ WRONG.** Six plain right-clicks logged `ctrl=1`
  (`[rcmenu] press#1..6 ... ctrl=1`). `TerminalInfoInteger(TERMINAL_KEYSTATE_CONTROL)`
  answers "held" on this build while nothing is held — the MQL4 reference says it
  returns GetKeyState()'s code, this terminal does not. **The gate is now
  `GetAsyncKeyState(VK_CONTROL) & 0x8000`** (user32, unambiguous), and the terminal's
  own property is still logged beside it as `ctrlProp=` so the mismatch stays visible.
  The gate is produced in the Full-only module and PUBLISHED through
  `RightClickTerminalOwns()` in UtilityFunctions (its askers straddle the Lite split).
  NOTE: by the same doc table, `TERMINAL_KEYSTATE_LEFT/RIGHT` are the ARROW keys, not
  mouse buttons — `UILeftButtonDown()` (P-UI-73) is reading an arrow key. Harmless so
  far (arrows are never pressed), but it is not a mouse probe.
- **B. THE OWNER TEST CANNOT PASS.** `menu=... NOT this chart's (owner=0 ...)`: MT4
  creates its menus with GW_OWNER 0 on this build. The test is now THE PRESS — a popup
  is judged only while THIS chart has a right press within 800 ms, which also keeps the
  user's Market Watch / Navigator menus untouched.
- **C. THE PRESS-EDGE ESC DOES NOT CLOSE IT.** `esc post=1 via=press-edge` and the menu
  was still there 244 ms later (MT4 has not created it yet at the press). The NET is the
  mechanism — and the net DOES run with the menu open (its own `menu=` line fired 244 ms
  after the press, inside the modal loop). The close now ESCALATES: 2 × posted
  WM_KEYDOWN, then a real injected `keybd_event` ESC; the line that reports the menu gone
  names which one did it (`[rcmenu] menu closed (closes=N last=postmsg|keybd_event)`).

Also measured: `[rcmenu] dll-ok hwnd=2556562 tid=9064` — every chart's window shares the
terminal's ONE message thread, as the design assumes; and `EURUSD,Weekly` still refused
(`Cannot call 'user32.dll::GetWindowThreadProcessId', DLL is not allowed`), i.e. that
chart's instance does not have the permission ticked.

14:14:53.555  menu=264066 ... -> ours to close          (+67 ms after the press)
14:14:53.555  close#1 via=keybd_event (net) menu=264066

Two defects visible in those four lines, both now fixed:
- `close#1 via=keybd_event` — the FIRST close already used the real keystroke, because
  `s_rcUseKey` was never reset when a menu closed: once escalated, every later close
  injected a system-wide ESC. It is per-menu state now.
- the 250 ms net is why the menu was visible for ~320 ms. **The cadence was the lever.**

### THE MEASUREMENT (external, no indicator on the chart, terminal pinned topmost)

Harnesses at the repo root: `_rc-when.ps1` (coarse), `_rc-race.ps1` (compiled loop,
~4 us a sample), `_rc-bench.ps1`. Guards that are NOT optional: the point must be the
terminal's chart VIEW (`WindowFromPoint`, checked AFTER the terminal is in front), the
cursor must be on the point, and the terminal must be foreground — one control run
reported "NO MENU" purely because a browser sat over the test point.

- **THE MENU IS CREATED ON THE BUTTON-DOWN, ~20 ms LATE.** `-Action down`:
  `DOWN-held: popup first seen at +24 ms ... rect=(300,162)-(506,815) size=206x653`, and it
  survives the release. `_rc-race.ps1` refined it to 17..27 ms, born at (0,0) with its
  final 206x653 size, then moved to the click point.
- **THEREFORE THE PRESS-EDGE POST IS DRAINED.** The terminal's idle loop eats the ESC in
  those ~20 ms. This is why finding C was true and why the net had to exist.
- **A LATE POST WORKS, AND ONLY A LATE ONE** (lever matrix):
  `esc-chart` ESC at t=13 ms → popup VISIBLE ≤1 ms · `cancel-post` WM_CANCELMODE at t=15 ms
  → visible 0 ms · `esc-popup` aimed at the popup → gone ~1 ms ·
  `cancel-send` SendMessage(WM_CANCELMODE), SYNCHRONOUS → does NOT work (menu lived 54 ms):
  a SENT message is handled inside the terminal's own press processing, the one moment the
  menu does not exist · `hide` ShowWindow(SW_HIDE) → overridden, MT4 re-shows the menu.
- **A PIXEL ORACLE IS IMPOSSIBLE HERE**: `GetPixel` on this composited screen measures
  16.6 ms a call (`_rc-bench.ps1`), so "did it paint" cannot be sampled from outside. The
  popup's VISIBILITY is the oracle; "≤1 ms visible" is as close to "never opened" as this
  platform allows, and the final judge is the user's eye.

### THE FIX

`RightClickOwner.mqh` gained a **fast window**: a plain press raises the housekeeping
cadence to `RC_FAST_MS` (1 ms asked) for `RC_WINDOW_MS` (900 ms) and every tick posts the
close again — so a tick lands in the ~20 ms between the press and the menu's creation and
the menu is ended on its loop's first message. `RightClickTimerHead()` is called FIRST in
`OnTimer` and returns true while the window owns the tick; the housekeeping below is still
let through on its own `RC_HOUSE_MS` (250 ms) due time, so ONLY the cadence changes. The
close is aimed at the POPUP once it exists (~1 ms) and at the chart while it does not
(~2 ms); `WM_CANCELMODE` joins after `RC_ESC_TRIES`, and `keybd_event` is now the LAST
resort after 12 posts instead of the second. A Ctrl press disarms the window, or it would
eat the menu the user asked for. The old `RightClickNet()` call in the entry is gone.

Verified: 11/11 root `.mq4` compile 0 errors; panel-wiring 348/348, probe-budget 259/259,
write-budget 56/56, gesture-budget 18/18, zorder 10/10, ui-text 11/11, chart-label 31/31,
panel-colour 19/19, base-count 159/159, submenu-geometry 1440 PASS.

**`probe-budget` was RED before this work and it was NOT this change**: the seed
"the armed/SET owner stops owning its flag" anchored on
`ObjectSetInteger(..., OBJPROP_SELECTABLE, armed);`, a line that no longer exists in HEAD
either — the owner publishes `want` inside an `if(... != want)` guard now (P-UI-98d/101).
Re-pointed to the guarded write it actually has. Lesson re-paid: a stale anchor turns the
whole audit into a permanent red that blames clean code.

## Win32 measurement lessons paid for in this session

- `GetMenuItemCount` / `GetMenuItemID` / `GetMenuString` take an **HMENU**, not an HWND.
  Passing the window handle silently answers 0 - it does not throw. This cost one full
  round trip ("popup has 24 items" -> "popup HMENU=0x0 items=-1").
- A PowerShell scriptblock handed to a native delegate runs in its OWN scope: `$script:x`
  reads as null there. Two probes died with "Cannot index into a null array" and one
  reported a false "0 visible popups" for this reason. Enumerate in C#, return a string.
- A `List<string>` returned from a static C# method to PowerShell enumerated as empty
  while `Count`-style reads worked; returning a joined `string` fixed it.
- `Add-Content` with no `-Encoding` writes ANSI, so `iconv -f UTF-16LE` garbles it.
  Read those scratch files with the Read tool, not iconv.
- A synthetic click needs the terminal FOREGROUND *and* topmost, asserted, or the click
  lands on the agent's own console and no menu is ever created - the failure looks like
  "MT4 has no context menu", which is the worst possible wrong answer.
